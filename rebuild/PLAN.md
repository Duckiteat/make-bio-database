# 재건 계획 (rebuilding project) — 글이 아니라 구조가 말하게

> 브랜치 `rebuilding-project` (2026-10-25 시작, main `4a84b40` 에서). 이 문서는 재건의 **목적·결정·방법·단계**를 적는다.
> 지금 숫자(파일 수·크기·분류 진행)는 이 문서에 쓰지 않는다 — `rebuild/status/` 가 자동으로 만든다(§6).

## 0. 미션

**모든 파일을 갈아엎는다는 생각으로 한다.** 문서·코드·시험·데이터 배치 모두 "지금 있으니까 둔다" 는 이유로 남기지 않는다. 파일마다 어느 모드에 속하는지, 무엇을 위해 있는지 다시 정하고, 그 자리를 구조가 말하게 한다.

지키는 것 하나: **검증은 끊기지 않는다.** 옮기는 동안 관문·시험·도장이 하던 판정은 그대로 돌아야 한다. 새 자리가 확인되면 옛 자리는 같은 단계에서 지운다(대체에는 제거 기한 — 결함 원인 ②).

## 2. 모드 — 어떻게 움직이나 (사용자 결정 2026-10-25)

작업은 **모드(어떻게 움직이나) × 대상(어디서 — TCA·MHC·텔로미어 …)** 으로 정한다. 모드를 먼저 고른다. 모드가 믿는 것·쓸 수 있는 곳·끝내기 전 시험·멈출 때를 정한다.

| 열쇠 | 모드 | 목적 | 쓸 수 있는 곳 | 가장 큰 위험 | 끝내기 전 (시험 묶음) | 멈춤 |
|---|---|---|---|---|---|---|
| `author` | **정보 작성** (수집가 역할 포함) | 실측에 매인 사실을 늘린다 | 패치 → 관문만. 수집가는 핸드오프만. 코드 편집 금지 | 지어내기 · 다른 종 값 | validate · 한계 후보 0 · 닿은 경로 audit-run · 거부 말뭉치 | 어휘에 없는 값 · 종이 다름 |
| `baseline` | **기초시험** (결정론장) | 지금 검증된 코어로 현실과 맞는지 본다 | 데이터·코드는 읽기만. 시나리오 숫자는 가정 원장. 사전 등록 뒤 실행 | 결과에 맞추려고 코드·데이터 고치기 | 무결성 PASS · 등록 해시 · 우연 기준선 · 등급 표기 (코드 시험은 바뀐 것이 없어 돌리지 않음) | 무결성 FAIL · AUDIT_* |
| `develop` | **디벨롭** | 기계(엔진·컴파일러·판정 규칙·도구)를 고친다 | 코드 — 사용자 요청 필수. 삼권 경계 | 데이터를 통과시키려고 규칙 완화 | 전체 시험 + 해당 엔진 시험 · 래칫 · 기록 한 행 | 완화가 유일한 길일 때 |
| `field` | **적분장** (T3 확률장 · T4 스파크 · T5 핵 기억) | 다음 엔진의 설계·시제품 | 엔진 시제품 + 그 시험. db 에 장 상태 금지 | 검증보다 능력이 앞섬 (direction §2) | p3·p5 종단 · 전이 수지 정확 0 · 벤치 | "반박할 공간 관찰이 있나?" 가 아니오면 결론 금지 |
| `inspect` | **점검·검증** (읽기 + 수집 정보 검증) | 상태를 읽고, 모은 후보를 판정한다 | db 쓰기 금지. **판정 결과와 승인 도장(증명 구역)만** 남긴다 (결정 ①) | 자기가 모은 것을 자기가 통과 | verify-collection · 인용–원문 대조 · attest | 1차 출처를 열 수 없음 → 사람 |
| `common` | 공통 | 모든 모드가 지킬 것 | — | — | — | — |

- **결정 ① (2026-10-25)**: 점검·검증 모드는 판정 결과(통과·거부·재검토)와 승인 도장만 남길 수 있다. db·패치는 쓰지 않는다 — 적용은 정보 작성 모드의 새 세션이 한다. 승인 도장까지 막으면 검증 결과를 남기려고 또 다른 세션이 필요해지기 때문이다.
- **수집과 검증을 가른다**: 정보 작성의 수집가가 모은 후보는 점검·검증 모드가 판정한다 — 자기가 모은 것을 자기가 통과시키는 고리를 끊는다(work-verification.md 의 원칙을 모드로).

## 3. 세션 규칙 — 한 세션 = 한 모드 (사용자 결정 2026-10-25)

- 세션은 **한 모드로 시작해서 한 모드로 끝난다.** 세션 안에서 모드를 바꾸지 않는다. 그래서 기초시험 중에 엔진을 고치는 길이 구조적으로 없다(승인 절차가 따로 필요 없음).
- 다른 모드가 필요하면 그 세션은 **전환 기록**을 남기고 끝난다. 다음 세션이 그 기록을 받아 새 모드로 시작한다. 전환 기록이 지금의 `workspace/handoff/NEXT-*.md` 산문을 대신한다.

전환 기록 (형식 초안 — 4단계에서 확정):

```json
{ "from": "baseline", "to": "develop", "at": "YYYY-MM-DD", "why": "한 줄",
  "target": ["D000148", "O000027"], "files": ["경로"], "open": ["다음 세션이 답할 질문"], "units": ["U…"] }
```

## 5. 분류 방법 — 언어보다 구조가 말하게

**단위는 문장 하나**다(파일이 아님 — 한 문단에 두 모드가 섞인 경우가 많다). 단위마다 장부 `rebuild/ledger/*.jsonl` 에 한 줄:

```json
{ "id": "U0001", "src": "CLAUDE.md:12", "text": "원문 그대로(긴 문장은 요지 + 원문 위치)",
  "mode": "author|baseline|develop|field|inspect|common", "kind": "rule|procedure|reason|value|history",
  "enforce": "machine|text|none", "where": "집행 자리(파일·함수·시험) — machine 일 때", "note": "" }
```

종류가 처리를 정한다:

| 종류 | 뜻 | 갈 곳 |
|---|---|---|
| `rule` 규칙 | 지켜야 하는 것 | 규칙 장부 — 집행 지점과 짝. `enforce: text` 면 기계로 올리기 · 보고서가 하게 · 지우기 셋 중 하나(build-plan 69) |
| `procedure` 절차 | 명령 순서·방법 | 모드 문서의 명령 순서(또는 명령 장부) |
| `reason` 이유 | 왜 그렇게 하나 | 규칙 번호에 붙은 이유 글 |
| `value` 현재 숫자 | 개수·크기·버전·분포 | 지운다 — 필요하면 생성 |
| `history` 역사 | 언제 무엇이 있었나·결과 일지 | 보관(읽기 경로 밖) |

`mode` 가 둘 이상에 걸치면 단위를 쪼갠다. 그래도 여러 모드가 쓰는 기준(등급·인정·종·한계)은 `common` 이거나, 한 모드에 두고 다른 모드는 번호로만 가리킨다 — 사본을 만들지 않는다.

## 6. 관리 파일 — 자동 갱신, 읽기 점검용

| 자리 | 무엇 | 누가 쓰나 |
|---|---|---|
| `rebuild/status/*.md` | 파일·문서·명령·판정·분류 진행의 개수와 크기 | 생성기 `node rebuild/status.mjs --write` → 서기 구역 `rebuild` 만 |
| `rebuild/ledger/*.jsonl` | 분류 장부(중간 파일) | 분류 작업 |
| `rebuild/PLAN.md` | 이 문서 | 사람·AI |

- **자동 갱신**: Claude Code 훅(`.claude/settings.json` 의 Stop)이 응답이 끝날 때마다 생성기를 돌린다. CI 와 `tests/rebuild.test.mjs` 가 `--check` 로 낡았는지 본다 — 파일 수·크기·건수가 바뀌었는데 관리 파일이 그대로면 실패한다.
- **읽기 점검용으로만**: 관리 파일은 사람과 AI 가 읽어서 점검하는 데만 쓴다. 다른 코드가 읽거나 입력으로 쓰지 않는다 — `tests/rebuild.test.mjs` 가 `rebuild/` 밖의 코드가 `rebuild/` 를 가리키지 않는지 검사한다(서기의 구역 표만 예외).
- 결정론: 관리 파일에 시각·난수를 넣지 않는다 — 같은 저장소면 같은 내용.
