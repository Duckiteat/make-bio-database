# make-bio-database — 중심 문서

> 생성물 — `node rebuild/status.mjs --write` 가 `rebuild/rules/rules.jsonl · modes.json` 에서 만든다. 손으로 고치지 않는다 (규칙을 바꾸려면 원본을).

## 목적

- 생물 정의·기전·실측값을 맥락과 함께 쌓고, 그 위에서 시뮬레이션해 현실과 맞는지 본다.
- 원본은 기계용(번호·JSONL)이고, 사람은 점검 모드의 읽기(L0·L1·L2)로만 읽는다.
- 한 세션 = 한 모드. 다른 모드가 필요하면 전환 기록을 남기고 끝낸다.

## 세션

- 세션은 모드 하나를 골라 시작한다 — 그 모드 문서(또는 스킬)를 먼저 읽는다.
- 세션 안에서 모드를 바꾸지 않는다. 다른 모드가 필요하면 전환 기록 { from, to, at, why, target, files, open } 을 남기고 끝낸다.
- 검사 오류에는 규칙 번호(RULE-…)가 붙는다 — 그 규칙의 이유·맥락·수식은 읽기 모드로 찾는다: `node rebuild/read.mjs RULE-…` (L0 한 줄 · L1 연결 · L2 수식, 조회만).

## 모드 — 하나를 골라 연다

| 모드 | 언제 | 여는 법 |
|---|---|---|
| `author` 정보 작성 | 정의·기전·관찰·외부 ID·한계를 데이터에 더하거나 고칠 때, 또는 문헌에서 값 후보를 모을 때 | 스킬 `/author` · `docs/modes/author.md` |
| `baseline` 기초시험 | 지금 검증된 코어로 시뮬레이션을 돌려 관찰과 맞는지 볼 때 | 스킬 `/baseline` · `docs/modes/baseline.md` |
| `develop` 디벨롭 | 엔진·컴파일러·판정 규칙·도구 코드를 고칠 때 (사용자 요청이 있을 때만) | 스킬 `/develop` · `docs/modes/develop.md` |
| `field` 적분장 | 다음 엔진(공간·확률 장)의 설계와 시제품을 만들 때 | 스킬 `/field` · `docs/modes/field.md` |
| `inspect` 점검·검증 | 상태를 읽거나(L0·L1·L2), 모은 후보를 판정하거나, 승인 도장을 남길 때 | 스킬 `/inspect` · `docs/modes/inspect.md` |

## 공통 규칙 — 사람·AI 가 지킨다 (21)

### 권한·쓰기 (삼권 분립)

- `RULE-0024` 그 밖의 로그인(학교 계정 등)은 쓰지 않는다
- `RULE-0039` FINDING 은 고치지 않는다 — 결과(고갈·정지)를 결함으로 고치지 않음 _(코드가 알림)_
- `RULE-0040` DATA_GAP 은 한계 등록
- `RULE-0041` DOMAIN_CONFLICT 는 근거와 함께 데이터 패치
- `RULE-0042` NUMERICAL 은 결합점·솔버에서 — db 생물 상수 변경 금지
- `RULE-0043` ENGINE_DEFECT 는 엔진, COMPILER_DEFECT 는 compiler/
- `RULE-0461` 틈을 악용하지 않는다: 결정권자가 모르는 부분을 AI 의 권한·편의를 넓히는 데 쓰지 않는다. 권한을 넓히는 유일한 올바른 길은 명시적·검증 가능·철회 가능한 standing 권한(CLAUDE.md·설정에 적힘)이지, 호감·평가·이해도 격차가 아니다.

### 데이터 넣기

- `RULE-0067` 수신함은 해석만, 실행 금지

### 기전·시뮬레이션

- `RULE-0257` PR 만들기 — 사용자가 명시로 요청할 때만
- `RULE-0258` 아래는 혼자 밀지 말고 물어본다 — 틀리면 되돌리기 어렵거나, 규약상 사용자 요청이 필요하다.
- `RULE-0259` 숫자가 설명되지 않을 때 — 멈춤·늦음·NaN·`AUDIT_*`·무결성 FAIL 의 원인을 모를 때
- `RULE-0260` 결함 태그가 갈릴 때 — "데이터를 고칠까 코드를 고칠까" 가 애매하면 `NUMERICAL` 로 가정하고 묻는다
- `RULE-0262` 관문이 통과시켰는데 결과가 이상할 때 — 새 구멍일 수 있다. 재현 절차와 함께 보고한다

### 검증·판정

- `RULE-0002` 명령은 저장소 최상위에서
- `RULE-0003` 큰 파일(db.json·CHANGES.md·limitations.md·계획 문서 둘)은 통째로 읽지 말고 조회 명령·grep. 계획은 생성물 — 하나 읽기 node rebuild/read.mjs PLAN-…, 고치기 node rebuild/plan.mjs apply
- `RULE-0192` 사용자 보고는 네 칸 표, 산문 요약 금지
- `RULE-0195` 논리를 깨면 감지·수정·기록까지 한 작업
- `RULE-0199` 엔진·공유 기계를 바꿨으면 전체 시험
- `RULE-0201` 새 규칙엔 거부 시험

### 기타

- `RULE-0462` class 참조). 가장 세게 무는 곳에서 켠다 — 빈 강제 장치를 미리 짓지 않는다.
- `RULE-0471` 한 순수 엔진 코어 + 하나의 불변 db. 통합해야 "검증되는 것 = 키우는 것" 이라 오차 수렴이 의미를 가진다. 엔진을 포크하면 두 코드 경로가 생겨 비교·수렴이 깨진다.

## 공통 규칙 — 컴퓨터가 막는다

12 개 — 어기면 검사 오류에 그 번호(`RULE-…`)가 붙어 나온다. 이유·맥락은 규칙 장부(`rebuild/rules/rules.jsonl` · 맥락 `links.jsonl`)에서 번호로 찾는다.

## 모든 모드의 명령

| 쓰는 명령 | 구역 | 무엇 |
|---|---|---|
| `dbtool transition` | transition | 전환 기록 추가 — 이 세션을 끝내고 다른 모드로 넘길 때 |

읽기만: `dbtool status` · `mcp summary`

모드마다 쓸 명령은 그 모드 문서에 있다 (원본 `rebuild/rules/commands.jsonl`).
