# DEC-0076 — develop 에 생성물 재생성 하나만 — 명령 장부 'dbtool limitations' 의 쓰는 갈래(--write)를 develop 에 허락 · limitations.md 직접 수정 권한으로 넓히지 않음

> 생성물 — 원본 `rebuild/state/plans.jsonl` · `rebuild/state/plan-log.jsonl` 에서 (`node rebuild/status.mjs --write`). 손으로 고치지 않는다 — 바꾸려면 `node rebuild/plan.mjs apply`. 계획: [build](../build.md)

`2026-11-23` · 사용자 (세션 답 2026-11-23 (원문 그대로)) · 설계

사용자: "Stage 0 (L000030)은 안 (가)를 조건부 승인한다. 단, develop에 부여하는 권한은 'dbtool limitations --write'라는 생성물 재생성 작업에 한정한다. 일반적인 limitations.md 직접 수정 권한으로 확대하지 않는다. … 1. 별도 DEC를 작성해 권한 변경의 근거와 범위를 기록한다. 2. 해당 명령이 기존 판정 데이터를 변경하지 않고 생성물만 재생성하는지 확인한다. 3. 재생성 결과와 원본 판정 데이터의 정합성을 finish check에서 검증한다. 4. L000030만 의도대로 변경되는지 확인하고 다른 limitation 상태가 불필요하게 변경되지 않는지 검사한다. 5. 테스트 및 전체 finish check를 통과시킨다. … 기존 데이터의 불필요한 변경은 금지한다. 모든 변경은 별도 결정과 검증을 거친다." 근거: 판정 코드(needMet)를 바꾸면 한계 상태가 바뀌고 생성물 limitations.md 가 낡는다 — 그 재생성 명령이 author · inspect 에만 있어 develop 커밋이 끝내기 시험(limitations.md 최신)을 통과할 수 없었다(PLAN-115 단계 0). 같은 재생성은 MCP 도구 write_derived(modes author · develop)로는 이미 develop 에 열려 있었다 — CLI 장부 줄만 좁았다. 범위: rebuild/rules/commands.jsonl 의 'dbtool limitations' 줄 modes 에 develop 을 더함. 그 줄의 writes_on '--write\b' 때문에 쓰는 갈래는 --write 하나뿐(다른 갈래 --check · --detect · --coverage 는 읽기). --write 는 db 를 읽어 judicial.limitationsMarkdown 으로 만든 글을 입법 서기 writeDerived('limitations') 로 limitations.md 한 파일에만 쓴다. 넓히지 않는 것: limitations.md 를 손으로 고치는 권한 — 손으로 고친 글은 끝내기 시험(tests/rules.test.mjs 'limitations.md 는 data/db.json 에서 생성된 최신 상태', 읽은 파일이 바뀌면 affected 가 늘 고름)이 거부한다. 모드 표(modes.json)는 바꾸지 않음. 철회: 그 줄의 modes 에서 develop 을 빼면 됨(rules.mjs apply).
