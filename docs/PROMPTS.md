# 프롬프트 묶음 — 이 저장소에 일을 맡기는 법

`docs/RUNBOOK.md` 를 읽은 에이전트(Sonnet 등)에게 일을 줄 때 쓰는 프롬프트와, 새 프롬프트를 직접 만드는 가이드.
**복사해서 쓰는 것이 목적이다.** `<…>` 만 바꾸면 된다.

---

## 0. 모든 프롬프트의 첫 줄 (고정)

작업 종류와 무관하게 이 두 줄을 먼저 붙인다. 이것만으로 사고의 절반이 사라진다.

```
먼저 docs/RUNBOOK.md 를 읽어라. 그게 이 저장소의 실행 설명서다.
data/db.json·CHANGES.md·limitations.md·교과서 부록을 통째로 읽지 마라 — 조회 명령(dbtool map/context/mechanism)과 grep 으로 필요한 줄만 본다.
```

세션이 `CLAUDE.md` 를 자동으로 읽으므로 규칙은 이미 들어가 있다. 설명서는 **조작**(무엇을 치나)을 준다.

---

## 1. 여섯 칸 틀 (이 순서로 쓴다)

좋은 프롬프트는 여섯 가지를 **명시**한다. 하나라도 비면 그 자리에서 추측이 일어난다.

| 칸 | 쓰는 것 | 비면 생기는 일 |
|---|---|---|
| ① 좌표 | 설명서를 먼저 읽어라 + 큰 파일 금지 | 토큰을 태우고 느려진다 |
| ② 임무 | **산출물 하나**를 구체적으로 (파일? 숫자? 보고?) | 범위가 번진다 |
| ③ 경계 | 건드려도 되는 것 / 절대 안 되는 것 | 규칙을 고쳐 통과시킨다 |
| ④ 검증 | 보고 전에 통과해야 하는 명령 | "됐습니다" 만 온다 |
| ⑤ 보고 | 네 칸 표 + 등급·가상·농도 공백 | 숫자의 신뢰도를 알 수 없다 |
| ⑥ 멈춤 | 무엇을 만나면 멈추고 물어볼지 | 혼자 밀다가 되돌리기 어려워진다 |

③과 ⑥이 가장 중요하다. **"통과하게 만들어라" 는 절대 쓰지 않는다** — 그 문장이 규칙을 느슨하게 만든다.
쓸 말은 **"거부되면 거부 메시지를 그대로 가져오고 데이터를 고쳐라"** 다.

## 2. 바로 쓰는 프롬프트

### A. 실험 돌리고 보고 (가장 흔한 일)

```
먼저 docs/RUNBOOK.md 를 읽어라. 큰 파일은 통째로 읽지 마라.

임무: <D000210 / telomere-hayflick> 실험을 돌리고 과정 보고서를 근거로 결과를 보고해라.
  node dbtool.mjs fate <상태> --scenario examples/scenarios/<시나리오>.json --report <보고서>.md --workers 8

경계: 데이터·코드·시나리오를 바꾸지 마라. 읽기와 실행만이다.

검증: 보고서 §3 무결성 증명서가 PASS 인지 먼저 확인해라. FAIL 이면 결과를 결론에 쓰지 말고 FAIL 로 보고해라.

보고: 네 칸 표(Scope·Why·Impact·Verification). 끝 상태만 말하지 말고
  결정 시점 · 변곡점 · 구간(기간·주된 원인·우세 표지·대사 비용) · 상수가 가상인지 · 농도 공백 표시를 함께 적어라.

멈춤: 무결성이 FAIL 이거나 AUDIT_* 가 나오면 원인을 추측하지 말고 그 줄을 그대로 가져와 보고해라.
```

### B. 문헌에서 상수 찾아 넣기

```
먼저 docs/RUNBOOK.md 와 docs/textbook/07-AI-작업-절차.md 의 §7.5′ 를 읽어라.

임무: <D000156/rule/oxidize 의 kcat·Km> 을 사람(9606) 값으로 문헌에서 찾아 데이터에 넣어라.

경계:
  - 값을 지어내지 마라. 찾지 못하면 한계(Kinetic_Gap)로 등록하고 그렇게 보고해라.
  - 다른 종(돼지·소 심장 효소)의 값을 사람 값으로 적지 마라 — 관문이 종을 대조해 거부한다.
  - 관찰 기록(O…)으로 먼저 넣고 규칙은 kinetics.from 으로 참조해라. 상수만 적으면 거부된다.
  - 불확도를 보고하지 않은 문헌 값은 sd 를 보고된 유효 숫자의 해상도로 적고 그 사실을 note 에 남겨라.
  - vocab.js·model.js·judicial/·legislative/ 를 고치지 마라. 거부되면 데이터를 고친다.

검증: node dbtool.mjs validate <패치> 가 통과한 뒤에만 augment apply 해라.
  넣은 뒤 전후를 비교해라 — '즉시' 였던 단계가 속도를 갖게 되면 궤적이 크게 바뀐다.
  node --test tests/*.test.mjs 와 validate·limitations --detect 를 돌려라.

보고: 네 칸 표 + 넣은 값마다 [값 · 단위 · 출처(DOI/PMID) · 등급] · 전후 비교 · 못 찾은 것은 한계 번호로.

멈춤: 거부되면 거부 메시지를 그대로 가져와라. 규칙을 고쳐 통과시키려 하지 마라.
```

### C. 정의항·기전 추가

```
먼저 docs/RUNBOOK.md 를 읽고, limitations.md 에서 이 작업이 닿는 한계를 grep 으로 찾아 읽어라.

임무: <개념/경로>를 데이터에 넣어라.

경계:
  - 먼저 node dbtool.mjs map 으로 이미 있는지 확인해라. 있으면 그 번호를 쓴다.
  - 새 번호는 임시 번호(D+1·S+1·O+1·L+1). meta.next 를 손대지 마라.
  - 기존 정의항을 고치는 패치는 배열이 통째로 교체된다 — 유지할 항목까지 전부 적어라.
  - 외부 ID 는 확실한 것만. 모르면 unmapped 에 사유를 적어라.
  - 새 정의항에는 addresses(어떤 한계를 어떻게 해결하나) 또는 gap_review 를 적어라.

검증: validate → augment apply → limitations --detect 후보 0 → node --test → audit-run <경로>.

보고: 네 칸 표 + 등록한 한계 번호 + audit-run 결과.

멈춤: 관문이 거부하면 메시지를 그대로. 통제 어휘(vocab.js)에 없는 값이 필요하면 멈추고 물어라.
```

### D. 시나리오 만들기

```
먼저 docs/RUNBOOK.md 와 비슷한 기존 시나리오(examples/scenarios/<가장 가까운 것>.json)를 읽어라.

임무: <무엇을 보이려는지>를 보이는 시나리오를 만들어라.

경계:
  - 확인되지 않은 상수는 시나리오에만 두고 hypothetical: true 를 선언해라. 데이터에 넣지 마라.
  - context { role, state, note } 를 반드시 적어라 — cause(원인) · requirement(없으면 이르지 못함) · baseline(신호 없음).
  - expect 를 실행 전에 적어라(입력 해시에 들어간다). 실행 뒤에 고치지 마라.
  - 억제 힐의 K 는 임계값보다 10% 아래에 둔다(SCHEMA §8L — K 에서 힐이 이미 절반 켜져 있다).

검증: 돌려서 무결성 PASS 인지 · 선언한 맥락과 실행이 일관한지(사법부가 판정한다) ·
  Δ(dt_slow)를 2배·4배로 바꿔 도달 시각이 같은지(근 찾기이므로 같아야 한다).

보고: 네 칸 표 + 맥락과 함께("이 실행은 X 의 원인을 보인다") + Δ 무관성 수치.

멈춤: 맥락 선언과 실행이 어긋나 FAIL 이면 시나리오 설계가 틀린 것이다. 멈추고 보고해라.
```

### E. 한계 정리·해결

```
먼저 docs/RUNBOOK.md 를 읽고 limitations.md 에서 <L000101> 을 grep 으로 찾아 읽어라.

임무: <L000101> 의 requirement.needs 를 채울 수 있는지 확인하고, 채울 수 있으면 데이터로 채워라.

경계: 확인된 값만. 못 채우면 왜 못 채우는지 requirement 를 더 구체적으로 고쳐라 —
  한계를 지우거나 해결된 것처럼 적지 마라. 한계 상태는 저장되는 게 아니라 계산된다.

검증: validate · limitations --check · --detect 후보 0 · 그 한계의 상태가 open → resolved 로 바뀌었는지.

보고: 네 칸 표 + 한계 번호의 전후 상태.

멈춤: 해결에 형식 변경(SCHEMA)이나 어휘 추가가 필요하면 멈추고 물어라.
```

### F. 레드팀 (안전장치 시험)

```
먼저 docs/RUNBOOK.md 와 SCHEMA.md §8M 을 읽어라.

임무: <공격 설명>이 지금 막히는지 확인해라.

방법: 저장소를 건드리지 말고 스크래치 폴더에 패치를 만들어 node dbtool.mjs validate 로만 시험해라.
  병합이 필요하면 사본에 해라: cp -r 로 복사한 뒤 --db <사본>/data/db.json.

경계: data/db.json 과 코드를 고치지 마라. 공격이 성공해도 고치지 마라 — 보고까지가 임무다.

검증: 막혔으면 거부 메시지를 그대로 가져와라. 통과했으면 그 결과가 엔진까지 닿는지(시뮬레이션 숫자가 바뀌는지) 확인해라.

보고: 공격별 표 [공격 · 판정(막힘/통과) · 거부 메시지 또는 오염된 숫자].
  통과한 것이 있으면 tests/fixtures/rejections/ 에 넣을 말뭉치 후보로 제안해라(넣지는 마라).

멈춤: 통과한 공격을 막는 코드를 쓰지 마라 — 그건 사용자 요청이 있어야 하는 규칙 변경이다.
```

### G. 진단 (숫자가 이상할 때)

```
먼저 docs/RUNBOOK.md 의 §3(결과 읽는 법)·§5(결함 태그)를 읽어라.

임무: <무엇이 이상한지 — 예: 텔로미어가 666.8 반복에서 멈춘다>의 원인을 찾아라.

방법: 고치지 말고 먼저 재현해라. 값을 하나씩 흔들어 민감도를 재라(ε 1e-12 ~ 1e-3).
  감사 항목의 fault 태그를 확인해라 — 그 태그가 고칠 자리를 정한다.

경계: 수치 문제를 db.json 의 생물 상수로 맞추지 마라(NUMERICAL). 결과(고갈·정지)를 결함으로 고치지 마라(FINDING).

보고: [증상 · 재현 절차 · 측정한 민감도 · fault 태그 · 고칠 자리 제안]. 고치지는 마라.

멈춤: 태그가 ENGINE_DEFECT·COMPILER_DEFECT 거나 판단이 갈리면 제안만 하고 멈춰라.
```

### H. 실측 정량 검증 (사전 등록된 규약 — 지금의 1순위)

```
먼저 docs/RUNBOOK.md §2(검증)·§3 과 docs/design/build-plan.md 항목 3·8 을 읽어라.

임무: <관찰 O… / 가설>을 사전 등록된 규약 아래에서 검증하고 과정 보고서로 결론을 내라.

선행조건(먼저 점검, 못 넘으면 여기서 멈춰 보고): 대응 실험의 종·세포·측정 시각·불확도·음성 대조가 있는가?
  정량이면 보류용 관찰이 use=validation 인가 — 지금은 정량 관찰이 전부 estimation(공백)이다.
  못 넘으면 그 출처 공백을 한계(Observation_Gap/Kinetic_Gap)로 등록하고 "규약 불가"로 보고해라(TAP 사례 L000107).

경계:
  - 규약(protocol)을 담은 시나리오를 실행 전에 register 해라 — 등록 뒤 고치면 미등록이 된다.
  - expect 를 실행 전에 적고 실행 뒤 고치지 마라. 음성 대조 없이 "일치" 라고 말하지 마라.
  - 데이터·규칙을 바꾸지 마라(검증은 읽기·실행). 값이 없으면 지어내지 말고 한계로.

검증: register 성공 → observe/evidence 의 무결성 PASS → 우연 기준선 P(K≥k) 와 함께.

보고: 네 칸 표 + 결론(맞음/틀림/보이지못함/무효) + 우연 기준선 + 맥락 이전 깃발 + 등급·가상 여부.

멈춤: 선행조건을 못 넘거나(출처 부족) 무결성 FAIL 이면 그 공백·메시지를 그대로 보고하고 멈춰라.
```

## 3. 다른 AI 를 함께 쓸 때

저장소에 접근하지 못하는 AI(웹 챗 등)는 **두 가지에만** 쓴다. 나머지는 손해가 더 크다.

| 쓸 만한 일 | 주는 것 | 받는 것 |
|---|---|---|
| **문헌 찾기** | "사람(9606) <효소>의 kcat·Km 을 원 논문에서 찾아 달라. 종·조건·불확도·DOI/PMID 를 반드시 같이. 없으면 없다고 해 달라" | 후보 값 + 출처 |
| **적대적 검토** | 코드·패치 조각과 "이게 틀릴 수 있는 경로를 찾아 달라" (내 결론은 주지 않는다) | 반례·놓친 경우 |

| 쓰면 안 되는 일 | 왜 |
|---|---|
| 상수·외부 ID 를 "대충 아는 값" 으로 받기 | 지어낸 값이 들어오면 전체 설계의 전제가 무너진다. **반드시 원 논문 식별자로 대조한다** |
| 결함 태그를 고르게 하기 | 저장소의 규약을 모른다 — 수치 문제를 데이터로 맞추라고 답하기 쉽다 |
| 패치 JSON 을 직접 쓰게 하기 | 관문의 형식을 모른다. 거부 메시지를 돌려줘도 규칙을 느슨하게 하자고 답한다 |
| 내 결론을 주고 검토 요청 | 그 결론을 확인해 주는 답이 돌아온다. 코드만 주고 판단은 받지 않는다 |

**다른 AI 에게서 온 값은 전부 "후보" 다.** 원 논문(PMC 전문·UniProt 큐레이션)에서 직접 확인한 것만 관찰 기록으로 들어간다.
확인하지 못하면 한계로 등록한다 — 그게 이 저장소가 다른 데이터베이스와 다른 점이다.

## 3′. 수집가·통합가 핸드오프 (싼 모델에 수집을 맡길 때)

비용을 아끼고 안전하게: **수집가(Sonnet 등)가 후보를 모으고, 통합가(Opus/사람)가 검증·적용·커밋한다.**
단위는 **묶음(batch)** — 항목마다 핑퐁하지 않는다.

**루프:** 통합가가 수집가에게 묶음 하나를 시킴 → 수집가가 읽기·조회·문헌으로 후보를 모아 **반환**(또는
핸드오프 파일에 `collected`) → 통합가가 **1차 출처로 재확인** → 통과분 패치 → `validate` → `augment apply`
→ 커밋 → 다음 묶음. 핸드오프 파일: `workspace/handoff/HANDOFF-<주제>.md`(AI 작업자 전용 공간 — `workspace/README.md`).

**수집가 권한 (A: 서브에이전트 / B: 상주 세션):**
- **A (서브에이전트, 지금 기본):** 보고만 — 구조적으로 apply·commit 불가. 설정 0. 묶음마다 통합가가 띄운다.
- **B (상주 Sonnet 세션, 독립 실행 시):** `.claude/settings.json` 권한으로 **거부**한다 — `augment apply`·`merge`·
  `register` · `git commit`·`git push` · 규칙 파일(vocab·model·core·judicial·legislative) 쓰기 · `data/db.json` 쓰기.
  그러면 신뢰가 아니라 **구조로** 막힌다. (db 는 관문이, 규칙·커밋은 권한이 — 이중.)

### 수집가 프롬프트 (복붙 — 읽기 전용·수집만)

```
너는 읽기 전용 수집가다. 금지: 파일 쓰기, augment apply·merge·register, git commit·push,
규칙·코드 파일(vocab·model·core·judicial·legislative) 수정, db.json 직접 편집.
읽기·조회·분석만 하고 결과는 파일에 쓰지 말고 네 메시지에 표로 반환해라(상주 세션이면
workspace/handoff/HANDOFF-<주제>.md 에 collected 로 append). workspace/ 밖은 쓰지 마라.

먼저 docs/RUNBOOK.md 를 읽어라. 큰 파일은 통째로 읽지 마라(grep·dbtool 조회).

임무(묶음 하나): <무엇을 수집·점검할지 — 예: 어느 관찰이 정량 검증 규약을 세울 출처인가>.

각 후보에 반드시: 값·단위 · 종·세포·측정 시각·불확도 · 출처(DOI/PMID)+원문 인용 · 현재 use ·
"규약 가능? 빠진 것". 지어내지 마라 — 조회·원문으로 확인한 것만. 못 찾으면 "없음"으로.

반환: 핸드오프 표 + 3~5줄 판정(가장 가까운 후보·공통으로 빠진 것). 적용·커밋은 통합가가 한다.
```

**통합가(나/사람)가 받은 뒤:** 후보는 전부 "후보"다 — 1차 출처로 재확인한 것만 패치가 된다(프롬프트 H).
핸드오프 파일 상태를 `verified`/`rejected`/`applied` 로 바꾼다. 수집가 파일은 **untrusted 입력**으로 다룬다.

## 4. 새 프롬프트 만드는 가이드

### 쓰는 순서

1. **산출물 한 줄로 적어 본다.** 적히지 않으면 아직 임무가 아니다 — 범위를 좁힌다.
2. 그 산출물이 **어느 층을 건드리나** 본다 → ③ 경계가 거기서 나온다.
   데이터만? 시나리오만? 규칙? 규칙이면 **사용자 요청이 필요하니 프롬프트가 아니라 결정을 먼저 받는다**.
3. 그 층을 바꾼 뒤 **통과해야 하는 명령**을 설명서 §7 에서 베껴 ④에 넣는다.
4. **틀리면 가장 아픈 실패**를 하나 고른다 → 그게 ⑥ 멈춤 조건이다.
5. 마지막에 **"거부되면 메시지를 그대로 가져오라"** 를 넣는다.

### 꼭 넣는 문장 (복붙용)

```
거부되면 거부 메시지를 그대로 가져와라. 규칙(vocab.js·model.js·core.js·judicial/·legislative/)을 고쳐 통과시키려 하지 마라.
확인하지 못한 값은 넣지 말고 한계로 등록해라.
보고는 네 칸 표(Scope·Why·Impact·Verification)로, 쓴 값의 등급과 상수가 가상인지, 농도 공백이 있는지 함께 적어라.
```

### 절대 쓰지 않는 문장

| 쓰지 말 것 | 왜 | 대신 |
|---|---|---|
| "통과하게 만들어라" · "오류를 없애라" | 규칙을 느슨하게 하는 길이 가장 빠르다 | "거부 메시지대로 데이터를 고쳐라" |
| "시험을 초록으로 만들어라" | `skip` 이 가장 빠르다 (래칫이 잡지만, 시간을 버린다) | "시험이 무엇을 요구하는지 보고해라" |
| "적당한 값을 넣어" · "대략" | 지어낸 값이 데이터가 된다 | "확인된 값만, 없으면 한계로" |
| "알아서 해" | 범위가 번지고 규칙을 건드린다 | 산출물 하나를 적는다 |
| "빠르게" | 검증을 건너뛴다 | 검증 명령을 ④에 적는다 |

### 프롬프트 점검 다섯 줄

새로 쓴 프롬프트를 이 다섯 줄로 본다. 아니오가 있으면 고친다.

1. 산출물이 **하나**이고 적혀 있나?
2. 바꿔도 되는 것과 **안 되는 것**이 적혀 있나?
3. 보고 전에 돌릴 **명령**이 적혀 있나?
4. **멈춤 조건**이 적혀 있나?
5. "통과시켜라" 류의 문장이 **없나**?

## 5. 작업이 끝난 뒤 (사용자가 확인할 것)

에이전트의 보고를 받으면 이 넷을 본다 — 설명서를 읽었는지가 여기서 드러난다.

| 확인 | 아니면 |
|---|---|
| 네 칸 표로 왔나, 산문 요약이 아닌가 | 규약을 안 읽었다 |
| 쓴 값의 **등급**과 **가상 여부**를 밝혔나 | 숫자의 신뢰도를 모르는 보고다 |
| 검증 명령의 **실제 숫자**(261/261, 오류 0)가 있나 | 돌리지 않았을 수 있다 |
| 거부가 있었다면 **메시지 그대로**가 있나 | 규칙을 고쳐 통과했는지 의심한다 — `git diff` 로 `vocab.js`·`judicial/`·`model.js` 를 본다 |

마지막 줄이 가장 빠른 점검이다: **규칙 파일이 바뀌었는데 사용자 요청이 없었다면 그 작업은 되돌린다.**
`tests/rejections.test.mjs` 가 자동으로 잡지만, 사람 눈으로도 한 번 본다.
