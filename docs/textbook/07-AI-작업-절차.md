# 7장. AI 작업 절차 (플레이북)

모든 명령은 저장소 최상위에서. 패치는 저장소 **밖**(스크래치 폴더)에 쓰고 `--dry` 부터.

## 7.0 세션을 시작할 때

```sh
node dbtool.mjs status                 # 규모·오류·다음 번호
cat limitations.md                     # 열린 한계 (새 개념을 설계할 거면 필독)
node dbtool.mjs prompt | less          # 작성 규칙·어휘·현재 색인
```

## 7.1 개념·정의항 넣기

1. 이미 있는지: `node dbtool.mjs map <이름|영문명|UniProt|CHEBI:…>` — 있으면 그 번호를 쓴다. 뜻이 여럿이면 `context` 로 맥락을 보고 고른다.
2. 패치:
```json
{ "format": "definition-db-patch", "version": 7, "why": "무엇을 왜 (Patch Report 의 Why — 필수)",
  "terms":  [{ "id": "T+1", "names": { "ko": "…", "en": "…" }, "aliases": [] }],
  "senses": [{ "id": "D+1", "term": "T+1", "kind": "protein", "reference_species": "9606",
               "xrefs": [{ "db": "UniProt", "id": "확인한 것만" }],
               "desc": [{ "text": "…", "field": "생화학", "context": { "scope": "…" },
                          "links": [{ "to": "효소#1", "rel": "is_a", "span": "효소" }],
                          "evidence": { "level": "curated", "sources": [{ "db": "DOI", "id": "10.…", "citation": "Kim et al., 2020" }] } }],
               "site": { "s32": { "type": "modification_site", "features": ["phosphorylated"], "numbering": { "9606": "Ser32" } } } }] }
```
3. 지킬 것: 복합체는 구성 요소를 **빠짐없이**, 모르는 잔기는 `residue_unknown: true`, 모르는 필수 ID 는 `unmapped`, 인용은 서지를 확인한 것만(못 하면 `abstracted` + `basis`).

## 7.2 기전(경로) 넣기

1. 원천부터: 각 분자의 부위·상태 의미 규칙·전이 규칙을 정의항에 둔다(규칙 = 그 변화를 일으키는 쪽이 소유, 결합은 부위가 바뀌는 쪽).
2. 단계는 규칙 참조 + 묶음만:
```json
{ "id": "S+1", "rule": { "owner": "D+1", "id": "phos" },
  "agents": [{ "ref": "D+kin", "features": { "act": "phosphorylated" }, "location": "cytosol" }],
  "inputs": [{ "ref": "D+1", "location": "cytosol" }, { "ref": "ATP", "location": "cytosol", "minor": true }],
  "outputs": [{ "ref": "D+1", "features": { "s32": "phosphorylated" }, "location": "cytosol" }, { "ref": "ADP", "location": "cytosol", "minor": true }],
  "part_of": ["경로 이름"] }
```
3. 위치는 묶음마다. 막을 넘으면 수송 단계(`transport`). 공간 접촉 오류가 나면 위치·면을 고친다(규칙을 느슨하게 하지 않는다).
4. 병합 후:
```sh
node dbtool.mjs mechanism "<경로>"                       # 사슬이 이어졌나
node dbtool.mjs simulate "<경로>" --until <출력> --from <입력>   # 유도되나 (음성 대조: --init "키=0")
node dbtool.mjs pattern "<경로>"                         # 상위 패턴 — 상위 개념이 없는 패턴이 두 경로 이상이면 7.4
node dbtool.mjs resolution "<경로>"                      # R2 가 필요한 단계 = 경쟁
node dbtool.mjs audit-run "<경로>"                       # Audit Error → 7.3
```

## 7.3 한계 등록하기 (실패를 데이터로)

언제: 시뮬레이션 실패·우회, 감사 오류, 단순화(화학량 차용, 부위 묶기), 확인 못 한 값.
```json
{ "limitations": [{ "id": "L+1", "target": "TNF 유전자/rule/kb_binding", "type": "Kinetic_Gap",
    "requirement": { "text": "무엇이 모자라 무엇을 못 하나",
                     "needs": [{ "kind": "kinetics", "rule": "TNF 유전자/rule/kb_binding", "params": ["Kd"] }] },
    "found_in": "어디서 드러났나" }] }
```
- 해결 경로는 **잘못 닫히지 않게** 구체적으로 (예: "PDB 아무거나"가 아니라 그 결합면을 담은 구조 → 형식으로 확인할 수 없으면 `manual`).
- 병합 후 `node dbtool.mjs limitations --write`, `--detect` 후보 0 확인.

## 7.4 상위 개념 만들기 (Evolution Engine)

1. `limitations.md` 를 먼저 읽는다.
2. Step A (아래에서 위로): 반복되는 패턴 → kind process + `motif`:
```json
{ "id": "D+kc", "term": "키네이스 연쇄", "kind": "process", "motif": "kinase_cascade",
  "desc": [{ "text": "…", "field": "세포생물학", "context": { "scope": "신호 전달 일반" }, "links": [],
             "evidence": { "level": "abstracted", "basis": "D…·D… 경로의 단계 구조에서 검출" } }],
  "addresses": [{ "limitation": "L000006", "how": "…(부분)" }] }
```
   해결하는 한계가 없으면 `gap_review` 에 이유. 둘 다 없으면 거부된다.
3. Step B (한계에서): 한계를 해결하는 새 개념(원리·모델)을 설계할 때 **엔진이 그 개념을 실제로 쓰게** 만든다(예: 구획 농도 모델 → 시뮬레이터가 copy_number·부피를 읽음). `addresses.how` 에 어떻게 자동 해결되는지 적는다.

## 7.5 속도 상수 넣기

- 확인한 값만 규칙의 `kinetics` 에, SI 정준 단위로, 근거와 함께. 종·조건은 `kinetics.context`.
- 협동 결합(예: cAMP 4분자)은 `binding` 이 아니라 `mass_action` + `order`.
- `Kd` 와 `k_on`·`k_off` 를 함께 적으면 10% 안에서 맞아야 한다.
- 엔진만 시험하려면 `examples/scenarios/*.json` 에 `hypothetical: true` 로 — 데이터베이스에는 넣지 않는다.

## 7.5′ 문헌에서 상수를 찾는 절차 (TCA 회로 조사 2026-10-10 에서)

1. **권위 DB 의 큐레이션부터.** UniProt 항목의 `BIOPHYSICOCHEMICAL PROPERTIES`(kineticParameters·note)에는 사람 효소의 Km·kcat 과 **그 근거 PubMed ID** 가 함께 있다(`https://rest.uniprot.org/uniprotkb/{acc}.json`). SABIO-RK 의 옛 REST 는 2026-10 현재 404 다.
2. **그 근거 논문의 전문에서 값을 직접 읽는다.** Europe PMC(`/europepmc/webservices/rest/search` → `{PMCID}/fullTextXML`)나 PMC efetch 로 표를 읽는다. 공개 접근이 아니면 **UniProt 이 큐레이션한 값까지만** 쓰고, 열람하지 못했다는 사실을 관찰 기록의 `note` 에 적는다.
3. **종이 다르면 넣지 않는다.** 돼지·소 심장 효소의 값을 사람 값으로 적지 않는다 — 찾지 못한 것은 한계로 등록한다(예: L000096).
4. **측정값은 관찰 기록으로, 규칙의 상수는 그것의 파생값으로.** 관문이 이것을 강제한다 — `evidence.level: curated` 인 kinetics 에 `from: [{param, obs}]` 이 없으면 거부된다(`observation-port.md §1`). 그래서 순서는 ① 관찰 기록(O…) ② 같은 패치에서 `kinetics.from` 으로 참조.
5. **불확도를 보고하지 않은 문헌 값**은 sd 를 **보고된 유효 숫자의 해상도**로 적고(예: `170 s⁻¹` → sd 10), "측정 표준 편차가 아니다" 를 `note` 에 남기고 `Observation_Gap` 을 등록한다(L000100).
6. **상수가 반쪽이면 규칙에 넣을 수 없다.** `michaelis_menten` 은 kcat·Km 을 모두 요구하므로, Km 만 찾은 효소는 관찰 기록으로만 남기고 속도 법칙은 비워 둔다(예: 시트르산 생성효소 O000007).
7. **ΔG°′ 는 계산해 둘 수 있다.** eQuilibrator 3.0(성분 기여법, DOI 10.1093/nar/gkab1106)에 **모델이 적은 반응식 그대로** 물어 ΔrG′° ± σ 를 받는다 — 측정값이 아니므로 `evidence.level: computed` + 도구 이름. 속도 법칙이 없는 규칙은 `kinetics` 칸을 쓸 수 없으니 관찰 기록으로만 남긴다.
8. **상수를 넣은 뒤 반드시 전후를 비교한다.** 속도 상수가 없던 단계는 '즉시' 로 처리되므로, 상수를 하나 넣으면 궤적이 크게 바뀐다 — 시트르산 회로에서는 '0.101 s 에 NAD⁺ 고갈' 이 사라졌다 — 측정 Km 2.35 mM 이 시나리오의 중간 대사물 농도보다 **10⁷ 배** 높아서 흐름이 거의 0 이 되기 때문이다(100 fL 에 아이소시트르산 10 분자 = 0.166 nM, Km/[S] = 1.4e7; NAD⁺ 3002 분자 = 49.8 nM 인데 측정값은 HeLa 기질에서 818 µM — BNID 112849, Chen et al., 2016, DOI 10.1016/j.cell.2016.07.040). 즉 병목이 **속도에서 농도로** 옮겨간다. 측정 상수가 제대로 쓰이는지는 Km 근처 농도의 민감도 시나리오로 확인한다(`tca-measured-kinetics-hypothetical.json`: 흐름 1362.6 회/s = kcat·[E]·S/(Km+S) 와 일치).

## 7.5A 생애 주기·대사물 저장소 넣기 (v7)

- **부분 구조**: ATP 처럼 반응에서 부분이 옮겨 다니는 분자는 `moieties` 를 단다(`아데노신 부분`·`구아노신 부분`·`인산기 단위` 정의항). 달면 그 분자가 낀 변환·분해·공급 규칙의 수지가 검사되므로, **빠진 산물(피로인산·Pi)을 같은 패치에서 규칙(`effect.produces`·`with.produces`)과 단계(minor 출력)에 함께 넣는다.**
- **공급 규칙**: 소비만 되는 저장소(AUDIT_RESOURCE)를 닫으려면 그 반응을 일으키는 효소 부류나 과정 정의항에 `supply` 규칙을 둔다. 효소가 없다면(원료를 모델 밖에 둠) process 정의항에 두고 `evidence: abstracted`. 원료가 정말 계 밖이면 `source: true`. 속도를 모르면 `kinetics` 를 비우고 Kinetic_Gap 등록.
```json
{ "id": "D+ndpk", "term": "T+ndpk", "kind": "molecule_class", "xrefs": [{ "db": "EC", "id": "EC 2.7.4.6" }],
  "rule": [{ "id": "gtp_regeneration", "type": "supply", "label": "GTP 재생",
             "consumes": [{ "ref": "GDP", "n": 1 }, { "ref": "ATP", "n": 1 }], "produces": [{ "ref": "GTP", "n": 1 }, { "ref": "ADP", "n": 1 }],
             "where": ["cytosol"], "evidence": { "level": "asserted" } }] }
```
- **분해 규칙**: 분해되는 정의항에 `degradation` 규칙. 단위체로 돌아가면 `fate: recycled` + `recycle_to`(화학량을 서열 길이로 쓰려면 `n: "sequence_length"` + `sequence_length` 관찰). 반감기는 확인한 값만 `kinetics: { law: "mass_action", order: 1, half_life }`.
- 시험은 `examples/scenarios/` 의 가상 시나리오(`reservoirs`·공급·분해 kinetics). `node dbtool.mjs simulate <경로> --rate --scenario … [--stochastic --seed 7] [--reservoirs infinite]` 후 `audit-run`.

## 7.5B 외부 ID 원본 대조 — 자동 보강 고리
1. 찾기: `node dbtool.mjs augment plan` — unmapped(필수 ID)·Identity_Gap 은 이름 검색 과제, asserted UniProt·ChEBI 는 직접 조회 과제, 서열 길이를 기다리는 한계(예: L000058)는 같은 과제에 연결된다. Patch Report 의 '자동 보강 후보' 수가 0 이 될 때까지.
2. 받기: `augment fetch` (curl, 프록시를 따름). 막히면 `data/fetched/RETRIEVAL_TASKS.md` 를 사용자에게 넘긴다 — 받을 주소·저장 위치·간이 JSON 형식이 적혀 있다.
3. 확인: `augment build` — 단백질은 번호·종·유전자/단백질 이름·중복, 저분자는 이름·화학식 원자 수 ↔ 부분 구조·중복. 표의 ✓ verified · ✗ rejected · ? ambiguous · → candidate(검색 후 항목 조회 과제가 새로 생김) · · missing.
4. 병합: `augment apply` — 관문 통과 시 db.json·기록·CHANGES.md 한 행. 그 뒤 `limitations --write`, `textbook --write`.
- 하지 말 것: 모호한 검색 결과에서 고르기, 다른 값의 asserted 를 덮어쓰기(`--sync` 는 사용자 요청 때만), 수신함 파일 고치기.

## 7.5B′ 추세 점검 — 등급 anchor 를 열고 싶을 때 (시간 축)

S(출처)·D(성질)는 "그때 맞았다" 까지만 말한다. `anchor`(기준값)는 "지금도 합의와 같다" 를 요구하므로 **같은 신원 확인을 더 새 원본에 다시 돌린다**. 웹 검색 결과를 데이터로 저장하지 않는다.

1. 받기: `node dbtool.mjs trend --fetch` — 합의 수신함 `data/fetched/consensus/` 에. **신원 수신함(`data/fetched/`)을 덮지 않는다** — 그건 신원 도장의 증거다.
2. 판정: `node dbtool.mjs trend [<D…>]` — `match`(같은 결론·같은 값) · `mismatch`(달라짐) · `unchecked`(새 원본 없음 또는 도장이 창을 넘김).
3. 기록: `trend --write` — 날짜가 박힌 도장(claim `trend`). 서기가 재검증 뒤에만 넣는다.
4. 확인: `node dbtool.mjs grade` — 추세 축이 붙은 등급 분포. 지문(S4·D4)이 `anchor` 로 올라간다.
- `mismatch` 면 값을 지우지 않는다 — 등급이 `legacy`(지난값, 비교에만)로 내려가고 `Consensus_Gap` 을 등록한다. **왜 달라졌는지가 데이터다.**
- 원천별 합의 창(`vocab.consensus.sources` — 판 주기: UniProt 56일 · ChEBI 31일)을 넘긴 도장은 다시 `unchecked` 다 — 기준값은 영구하지 않다. 만료 전에 `trend --fetch` 로 다시 받는다.
- 도장이 증명하지 못하는 것: 그 원본이 **실제로 더 새 것인지**는 바이트로 알 수 없다(한계 L000085). 그래서 창으로 만료시킨다.

## 7.5C 비교 검토와 정제 (Comparative Optimization)
- 데이터 패치: 초안 → `node dbtool.mjs validate <patch.json>` (관문 + 정제 점검: 새 중복·등록 안 된 화학량 모순이면 거부) → `node dbtool.mjs augment apply <patch.json>` (병합·기록·CHANGES 행·limitations.md·부록).
- 새 규칙·수식·수치 선택: `node dbtool.mjs compare --state <세포 상태> --scenario A.json [--scenario-b B.json | --patch p.json] [--hours h]`. 표의 복잡도(규칙·조절 수, N_sub, 시간), 수치 L2(각 변형의 수렴 기준 대비), 결과(최종 상태·결정), 두 변형 사이 궤적 L2 를 보고 판정한다.
  - Optimization-Negative: 결과 같음 + 비용 ↑ + 이득 < 1e-5 → 넣지 않는다 (예: 같은 IL-12 → 해당과정 조절을 하나 더 — 복잡도 +4.0%, 궤적 차 0; 느린 단계 Δ 60 → 30 s — 시간 +47–70%, 수치 L2 3.5e-4 → 4.4e-4).
  - Behavior-Changing: 결과가 바뀜 (예: 허가 조절 힐 n=2 → 1 — 결정 1.32 → 1.02 h). 두 수식 모두 자기 수렴 기준에 맞으므로 수치로 고를 수 없다 → 측정값으로, 없으면 한계 note 로.
- 정제 점검은 `augment`·`simulate --rate`·`fate` 가 끝날 때마다 자동으로 나온다 (○ known · △ 고칠 것).

## 7.5D 정성 관찰 넣기 — 논문 → 0 층 → 모의 판정 (build-plan 10 에서)

1. 1차 문헌을 고른다(교과서·리뷰의 요약은 안 됨). 초록을 서기 `fetchToInbox` 로 `data/fetched/europepmc/MED-{PMID}.json` 에 받는다 — Europe PMC `search?query=EXT_ID:{PMID} AND SRC:MED&resultType=core&format=json`.
2. `quote` 는 받은 원문에서 그대로 옮기고(받은 파일과 대조), `provenance.sha256` 에 그 파일의 해시. 교란·읽을 거리를 모델 번호로 옮길 때의 대응(예: 'TAP 결손' → TAP1·TAP2 를 구성 요소로 가진 복합체 knockout)은 `note` 에 밝힌다. 원문에 없는 세포 유형은 적지 않는다.
3. `validate <패치>` → `merge` → `qualgraph O…` → `observe O… --state <상태> --scenario <대조군>`.
4. 검증 결론이 필요하면 대응 실험(세포·조건·측정 시점)을 원문에서 확인해 규약을 선언하고 `register` 뒤에 실행한다. 확인할 수 없으면 판정 수준은 '탐색' 이고, 막는 것을 Observation_Gap 으로 등록한다(지어내지 않는다).
5. 교란 실험 시나리오가 필요하면 파생 시나리오 `{ base, perturbation }` 로 — 복사본을 만들지 않는다.

## 7.5E 수집 후보 판정 — 인용을 원문과 대조 (`verify-collection`, build-plan 58)

수집가(사람·싼 모델·외주 에이전트)가 넘긴 핸드오프 후보는 자기 보고가 아니라 이 판정으로 상태가 정해진다.

1. 원문을 수신함에 받는다 — `mcp/fetch.mjs`(`fetch_abstract`·`fetch_fulltext`, 공개 전문만, 받기 기록 남음).
2. `node dbtool.mjs verify-collection <핸드오프>.jsonl`(또는 MCP `query.verify_collection`).
3. 후보마다 인용을 원문과 대조한다(`collection_audit.quoteCheck`): 태그·엔터티를 걷고, 유니코드·대시·따옴표·공백을 맞추고, 전문의 참고문헌 목록은 뺀 뒤 **글자 그대로 부분 문자열**인지 본다.

| 경우 | 판정 |
|---|---|
| 초록이나 전문에 있음 | 대조 문제 없음 (값 후보는 여전히 통합가 재확인 — REVIEW) |
| 전문이 있는데 없음 | **REJECTED** — 없는 인용이거나 숫자를 고쳐 쓴 인용 |
| 초록만 있고 거기 없음 · 원문이 없음 | REVIEW — 전문을 받거나(공개면) 사람이 확인 |
| 그림·표 전사(`transcribed: true`) · 12자 미만 인용 | REVIEW — 글로 대조할 수 없음 |
