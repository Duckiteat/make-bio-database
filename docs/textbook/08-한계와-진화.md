# 8장. 한계와 진화 — 시스템이 자기 한계를 설계도로 쓰는 방식

## 8.1 왜 한계를 데이터로 두나

실패를 로그 한 줄로 넘기면 같은 실패가 다른 경로에서 반복되고, 무엇을 채우면 나아지는지 아무도 모른다. 이 시스템은 실패·우회·추정·단순화를 **대상이 정해진 구조화된 기록**(L…)으로 남기고, 각 기록에 **해결 경로**(정확히 어떤 데이터가 들어오면 닫히는지)를 둔다. 그러면

- 한계는 데이터가 들어오는 순간 **자동으로** 닫히고(`limitationStatus`),
- 감사 오류는 **어느 한계를 채우면 되는지**를 제안하며(`gapSuggest`·`massSuggest`),
- 새 개념은 **어느 한계를 겨냥하는지** 적어야만 저장된다(`addresses`/`gap_review`).

## 8.2 세 종류

| 종류 | 무엇이 모자라나 | 해결 경로의 전형 |
|---|---|---|
| Kinetic_Gap | 속도(kcat·Km·k_on·k_off), 친화도(Kd), 시간 상수 | `kinetics` (규칙의 상수) |
| Concentration_Gap | 몰 농도, 세포당 분자 수, 구획 부피, 질량 수지 | `obs` (copy_number·concentration·compartment_volume) |
| Structural_Gap | 3차원 좌표, 잔기 번호, 화학량, 막 위상 | `residue`, `xref`(PDB), `manual` |

## 8.3 진화 루프

```
① 발견    simulate · simulate --rate · audit-run · 변환 · 시연에서 실패·우회·단순화
② 기록    patch.limitations[] → merge → limitations --write
③ 설계    새 개념을 만들기 전에 limitations.md 를 읽고, 그 개념이 무엇을 어떻게 해결하는지 addresses 에
④ 구현    개념이 '이름'에 그치지 않도록 엔진이 그 개념을 쓰게 한다 (필드·검사·시뮬레이터)
⑤ 채움    확인된 데이터(관찰·잔기·ID·속도 상수)가 들어오면 해당 한계가 자동 resolved
⑥ 감사    audit-run 이 남은 위반을 다시 한계로 연결 → ①
```
