# 엔진 입문과 질의응답 — 오늘 나눈 내용 전부 (2026-11-02)

> 목적: 엔진을 처음 접하는 사용자에게 개념을 차근차근 설명한 내용과, 그 과정에서 나온 질문·답을 기록한다. 1호·2호(`2026-11-01-engine-teardown*.md`)의 용어를 풀어 쓴 입문서 겸 기록이다.
> 칸: 범위 · 이유 · 영향 · 확인. 비유는 이해를 돕는 장치이고, 코드가 실제로 하는 일은 `확인` 칸의 근거로만 읽는다.
> 이 보고서도 코드를 고치지 않았다. 이번에 새로 잰 것은 §5 의 속도 상수 개수 하나다.

## 1. 레슨 1 — 엔진이 하는 일과 시간 걸음

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| 엔진이 하는 일 | 세포 안 물질의 양이 시간에 따라 어떻게 변하는지 계산한다. 한 번에 못 풀어서 시간을 잘게 나눠 조금씩 앞으로 간다 | 상태(물질별 개수) · 규칙(변하는 속도) · 걸음(시간 한 칸) 세 가지가 전부다 | `core.js`, `fate_engine.js` |
| 일정한 걸음(오일러, 속도 엔진) | "지금 속도로 한 걸음 쭉 간다"고 계산한다. 걸음 크기 `dt` 는 사람이 정해 고정한다 | 걸음이 길면 도중의 변화를 놓치고 짧으면 오래 걸린다. 걸음을 0.01 s → 0.001 s 로 바꾸면 LPS 끝 값이 상대 6.5e-5 달라진다 | `core.js:662`, 1호 E2 |
| 강성 | 세포 안에는 0.0001 s 에 끝나는 반응과 며칠 걸리는 변화가 섞여 있다. 일정한 걸음은 가장 빠른 것에 맞춰야 해서 끝나지 않는다 | 걸음 크기를 상황에 맞게 바꾸는 방식이 필요하다 | 사용자가 보낸 두 번째 글 |
| 적응형 걸음(운명 엔진) | 한 걸음을 두 가지 정밀도로 계산해 차이를 본다. 작으면 받아들이고 다음 걸음을 키우고, 크면 거부하고 줄여서 다시 한다. Rodas3 가 이 방법의 이름이고 빠른 반응이 있어도 터지지 않는 성질(L-안정)을 가진다 | 이 부분은 운명 엔진에 이미 있다. 속도 엔진에는 없다(PLAN-080 의 이유) | `fate_engine.js:90–191`, 사용자가 보낸 첫 번째 글 |
| 관찰 격자(`dt_slow`, 기본 60 s) | 내부 걸음은 가변이지만 신호 켜기·기록·결정 검사는 60 s 마다 한 번 "사진을 찍을 때"만 한다 | 사진 눈금과 실제 시간을 잇는 곳에서 결함이 생긴다 | `fate_engine.js:312–349` |
| 시계 결함 3 가지 | K3: 마지막 구간이 짧으면 기록 시각이 틀린다(적분 끝 100 s, 기록 120 s). K4: 신호가 사진 시점에서만 바뀌어 100 s 신호가 120 s 에 켜진다. K1: 속도 엔진이 `t_end` 를 넘겨 돈다(5 s 요청 → 5.04 s) | 1호 §2 에서 측정으로 확인 | `scratchpad/clock_probe.js` |
| 지금까지 안 드러난 이유 | 시나리오 24 개의 `t_end` 와 신호 시각이 모두 60 의 배수다 | 잠재 결함. 새 시나리오가 배수가 아니면 처음 틀린다 | 2호 §3 |

## 2. 레슨 2 — 확률 층

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| 평균 계산의 한계 | 분자가 많으면 운이 상쇄돼 평균과 같지만, 몇 개뿐이면 "언제 일어나는지"가 운이다. 같은 세포 100 개도 서로 다르게 변한다 | 평균 계산은 이 차이를 지운다 | 1호 E5 |
| 세 가지 방식 | 분자 1 만 개 이상: 평균(Rodas3) · 100 개 미만: SSA(다음 사건의 시각을 주사위로 정하고 하나씩 일으킴) · 중간: τ-도약(짧은 시간의 사건 수를 한 번에 뽑음) | 반응마다 분자 수를 보고 고른다. 전환 문턱은 임의의 선택이다 | `coupling.js:22–23` |
| 시드와 난수열 | 컴퓨터는 공식으로 주사위 같은 숫자 열을 만들고, 출발점이 시드다. 같은 시드면 같은 열이다 | 재현이 된다는 장점 | `rng.js` |
| 줄 서서 뽑는 번호표 | 난수를 줄 순서로 하나씩 쓴다. 걸음이 거부되면 뽑힌 번호가 버려진다("난수는 이미 썼다"). 걸음이 달라지면 이후 번호가 전부 한 장씩 밀린다 | 같은 시드라도 `rtol`·`dt_slow`·`atol` 이 바뀌면 경로가 완전히 달라진다. 변경 전후의 공정한 비교가 불가능하다("시드 표류") | `fate_engine.js:265–272`, DEC-0045 |
| 해결책(PLAN-020) | 번호표를 사건에 붙인다. "3 번 세포의 7 번째 반응"에는 항상 같은 난수가 나온다 | 규칙 하나만 바꾼 두 실행을 같은 난수로 비교할 수 있다. 기존 궤적이 한 번 바뀌므로 사용자 확인이 필요하다 | PLAN-020 |
| 속도 엔진의 확률은 반쪽 | `stochastic` 이 분해 규칙에만 이항 추출을 쓴다. 반응·공급은 평균 계산 그대로 | 이름은 확률 실행인데 일부만 확률. 결과에 이 표시가 없다 | `core.js:708–711` |

## 3. 질문과 답 — 변하는 이유는 무엇인가

**질문**: 결과가 달라지는 이유가 그냥 확률인가, 국소 농도에 의한 보정 확률인가, 반응물끼리 만날 확률을 따로 잡는가.

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| 운이 정하는 것 | 반응이 **언제** 일어나는지다. 일어날 빈도(속도)는 평균 계산과 같은 속도식에서 가져온다 | 평균 계산과 확률 계산이 같은 속도식을 쓴다. 확률은 그 값을 주사위로 정수 개수의 사건으로 바꾼다 | `fate_engine.js:107–111` |
| 국소 농도 보정 | 없다. 농도는 "분자 수 ÷ (아보가드로 수 × 구획 부피)" 로, 구획 전체의 평균이다("잘 섞여 있다" 가정) | 구획 안의 위치 차이는 계산에 안 들어간다. 위치 효과는 공간 엔진(적분장, 4 부)의 일이고 현재 코드에는 없다(DEC-0032) | `tape.js` CONC, PLAN-028–036 |
| 반응물이 만날 확률 | 분자를 개별로 추적하지 않고 종류별 개수만 센다. 만남은 속도식에 녹아 있다 | 충돌을 따로 계산하지 않는다 | `fate_engine.js` `N` 배열 |
| 같은 분자끼리의 반응(2A → …) | 수식 테이프가 농도를 거듭제곱(`POW`)한다. 표준 확률 계산은 N·(N−1)/2 에 비례해야 한다 | N 이 클 때는 차이가 없으나 N 이 2–3 개이면 반응 가능성이 과대평가될 수 있다. **테이프만 보고 한 추정이고 확률 층이 따로 보정하는지는 확인하지 못했다. 1호에는 적지 않았으므로 확인할 항목이다** | `compiler/tape.js` 의 POW 명령(case 8) |
| 효소·힐 식을 확률에 사용 | 미카엘리스–멘텐과 힐은 평균 농도용 식인데 확률 층에서도 그대로 쓴다 | 분자가 적으면 근사가 나빠진다. 1호가 이미 "등록되지 않은 한계"로 지적했다 | 1호 E5 |

## 4. 질문과 답 — 분자가 부딪히는 각도는 희생되는가

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| 압축되어 남는 것 | 충돌 각도·방향·에너지는 사라지지 않고 **속도 상수 k 하나에 평균으로 뭉쳐** 들어간다. 실측한 k 에는 이미 그 사정이 담겨 있다 | k 가 실측에서 오는 한 이 압축은 정당하다. 일부 규칙은 에너지 장벽과 온도로 k 를 계산하는데(`k0·exp(−ΔG/RT)`), 이것도 각도를 푸는 것이 아니라 장벽 높이 하나로 압축하는 방식이다 | `core.js:407–412`, `SCHEMA.md:332` |
| 정말 사라지는 것 | 분자의 위치 · 개별 분자의 이력 · 확산 속도(섞이는 시간을 0 으로 봄) · 세포 안 혼잡 효과 · 같은 이름표 안의 입체 구조 차이 | 분자 수가 아주 적을 때, 확산이 반응보다 느릴 때(막 근처 등), 위치가 기능을 정할 때 틀린다 | 앞 질문의 답, 가정 한계 |
| 이렇게 버리는 이유 | 분자 하나하나를 시뮬레이션하면 세포 하나(분자 수십억 개)를 며칠 단위로 돌릴 수 없다 | 이 저장소의 목적(긴 시간 척도의 세포 운명 결론)에 맞는 선택. 위치별 농도는 적분장 모드의 목표이고 분자 단위(분자동역학)는 범위 밖이다 | `CLAUDE.md` 목적, 4 부 |

## 5. 질문과 답 — 속도 상수 k 는 어디서 오는가 (이번에 잰 값)

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|

| 시나리오 44 개 중 가상(`hypothetical`)이 43 개 | 속도 상수 대부분이 시나리오에서 "가정 값"으로 들어온다. 시나리오가 직접 적은 속도 상수 항목의 합은 794 개이다(여러 시나리오에 중복 포함) | 지금의 시뮬레이션 결과는 대부분 가정 값 위에서 돈다. 앞 보고서의 "검증 엄격성 ↔ 실측 유입 (치명)" 판단과 같다 | **측정**, `2026-10-25-architecture-analysis.md` §3.1 |
| `kinetic_constant` 관찰 | 0 건 | 속도 상수를 관찰로 직접 올린 건 없다. 4 개의 실측 상수는 다른 종류의 관찰에서 파생된 것이다 | **측정** |
| k 가 들어오는 길 | ① 데이터 규칙의 `kinetics` ② 시나리오가 덮어쓰기 ③ 에너지 장벽과 온도에서 계산(`k0`, `dG_act`, `dG0`) | 우선순위는 시나리오 > 데이터. 가정 원장(`dbtool assume`)이 출처를 드러내지만 인라인 숫자가 남은 시나리오가 있다 | 1호 E9, 앞 D1 |
| 의미 | 엔진이 아무리 정밀해도 결과의 정밀도는 k 의 근거에서 막힌다 | 엔진 개선과 별개로 **실측 유입**이 결론의 신뢰를 정한다. 정보 작성 모드의 일 | 앞 §3.2 |

## 6. 레슨 3 — 두 벌의 엔진(JS 와 Rust), 그리고 "비트 일치"

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| 왜 두 벌인가 | JS 판은 읽기 쉬운 **정답지(오라클)**이고, Rust 판(WASM 으로 컴파일)은 **빠른 실행용**이다. 같은 알고리즘을 두 번 만들어 서로 맞는지 확인한다 | 한쪽의 오류를 다른 쪽이 잡는 장치다. 대신 코드가 두 곳이라 고칠 때 둘을 같이 고쳐야 한다 | `fate_engine.js`, `engine/rust/src/engine.rs` |
| 비트 일치란 | 컴퓨터는 소수를 한정된 자릿수로 저장한다. 같은 식이어도 계산 순서나 내장 함수(거듭제곱·로그·지수)의 구현이 다르면 맨 끝자리가 다를 수 있다. 계산기 두 대가 1/3 을 16 번째 자리에서 달리 반올림하는 것과 같다 | "비트 일치" = 맨 끝자리까지 정확히 같다 | `engine.rs:6` 주석 |
| 지금 어디까지 같은가 | 시험이 보장하는 것: Rust 를 다시 돌리면 같음(④) · 네이티브 = WASM 은 비트 같음(⑤) · JS 대 Rust 는 `rtol` 안에서만 같음(② MHC ⑥) · 출생–사멸 확률 모델은 JS = Rust 비트 같음(⑧) | 연속 계산은 끝자리 차이가 걸음마다 다시 작아지거나 일정해서 `rtol` 안에서 문제 없다 | `tests/rust_engine.test.mjs`, `tests/mhc.test.mjs:128` |
| 끝자리가 왜 문제가 되는가 | 연속 계산에서는 작은 차이가 작게 남는다. 그런데 엔진에는 **이산 결정**이 있다: 걸음을 받아들일지 거부할지 · 확률 층의 난수를 받아들일지 버릴지 · 어느 반응이 먼저 일어날지. 끝자리 차이가 이 결정을 뒤집으면 그 뒤의 경로가 갈라진다(나비 효과) | 결정론 실행은 `rtol` 안에서 안전. **확률 실행은 JS 와 Rust 의 경로가 완전히 갈라질 수 있다 — 의심이지 측정이 아니다** | 1호 E7 |
| 차이의 원인 | 걸음 크기 갱신과 힐의 거듭제곱을 JS 는 V8 의 `Math.pow`, Rust 는 순수 Rust 의 `libm::pow` 로 계산한다. 난수 쪽 `log`·`exp` 도 마찬가지다 | 같은 입력에서 마지막 자리가 다를 수 있다 | `engine.rs:310·314·398·442`, `tape.rs:50`, `rng.rs:43–58` |
| FMA 라는 변수 | 일부 컴퓨터는 "곱하고 더하기"를 한 번에 해서 반올림을 한 번만 한다(FMA). 컴파일러가 이걸 쓰면 같은 Rust 코드도 기계에 따라 끝자리가 달라진다 | `Cargo.toml`·`build.sh` 에 FMA 를 막거나 허용하는 설정이 보이지 않는다. 기본 대상 설정에서는 FMA 를 안 쓸 가능성이 높다고 알고 있으나 이번에 컴파일 결과로 확인하지 않았다 — 지금 일치가 설정이 아니라 기본값 덕일 수 있다 | `engine/rust/Cargo.toml`, `build.sh` |
| 해결책(PLAN-021) | 거듭제곱·로그·지수를 정수 연산으로 직접 구현해서 두 엔진이 같은 코드를 쓰게 하고, 외부 수학 함수 호출 0 · FMA 금지를 못 박는다 | JS 와 Rust 가 비트까지 같아진다. 열역학 속도(`exp`)의 마지막 자리가 바뀐다(NEXT 문서) | PLAN-021 |
