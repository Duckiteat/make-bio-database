# 반복 기록 일의 자동화와 파일 탐침 (2026-11-01)

> 왜 작업 하나에 도구 호출과 토큰이 많이 드는지 이번 세션의 영수증으로 재고, 무엇을 자동화하면 얼마나 줄어드는지 추정한 보고서.
> 계획 항목은 STG-11a–e (`node rebuild/read.mjs STG-11a`). 칸: 범위 · 이유 · 영향 · 확인.

## 1. 목적과 지키는 선

- **목적**: 기록 규약(맥락·이유를 남김 — DEC-0022)은 그대로 두고, 그 규약을 지키는 **손일과 다시 돌리기**를 줄인다.
- **지키는 선**:
  - 이유·영향·사람이 읽는 설명은 자동으로 쓰지 않는다. 기계는 초안과 빈칸만 만든다.
  - 문지기와 자기 검사 장치는 건드리지 않는다. 바꾸는 것은 기록하는 도구뿐이다.
  - 자동화된 도구도 같은 장부 사건(봉인 · 이유)을 남긴다. 사람이 손으로 한 것과 기록이 같아야 한다.

## 4. 파일 탐침 — 설계

새 색인을 손으로 만들지 않는다. 이미 있는 기계 자료를 엮는다. 손으로 적은 지도는 낡지만, 엮은 지도는 원본이 바뀌면 같이 바뀐다.

| 원천 | 주는 것 |
|---|---|
| 규칙 장부 `where` · 집행 장부 `file` · `tests` | 규칙 번호 ↔ 판정 코드 자리 ↔ 시험 |
| 시험 추적 지도(`tests/trace.mjs`가 만드는 것) | 파일 → 그 파일을 읽는 시험 |
| 계획 항목의 `자리` · `무엇` | 작업 번호 → 코드 자리 |
| git 함께 바뀜 (§2 표) | 파일 → 보통 같이 고치는 파일과 그 비율 |
| 단위 장부(`rebuild/ledger/units.jsonl`)의 src | 문서 줄 → 분류 (줄을 더할 수 있는지, 이어 써야 하는지) |
| 반복 작업 처방 (적은 수, 코드 곁에) | "기계 규칙 추가" · "관찰 칸 추가" · "어휘 표 추가" · "새 파일" 때 반드시 닿는 자리(저장 지도 · SCHEMA 변경 기록 · 교과서 · 계약 스키마 등) |

출력 예 (`probe.mjs judicial/judicial.js` — 모양만 보이는 예. 규칙 수와 비율은 2026-11-01 값):

```
판정 코드 — 규칙 133 개 (RULE-0525 checkReported · RULE-0526 checkUnitSystem …)
시험 — tests/observations · rules · rebuild · assays … (추적 지도)
같이 고침 — CHANGES 94 % · SCHEMA 81 % · model.js 62 % · vocab.js 62 %
처방 — 판정 규칙을 더하면: 규칙 한 번에(rules.mjs rule) · SCHEMA §… · 교과서 3 장 177 줄(이어 쓰기 — 분류된 줄)
```

탐침은 읽기만 한다. 영수증에도 읽기로 남는다.

## 7. 하지 않는 것

- SCHEMA · 교과서 문장, CHANGES의 이유·영향 칸은 자동으로 쓰지 않는다.
- 문지기 훅 · 영수증 · 자기 검사 장치는 바꾸지 않는다(장부로도 열 수 없는 자리).
- 시험을 건너뛰지 않는다. 사전 검사는 전체 시험을 **대신하지 않고 앞에 선다**. push 전 전체 시험은 그대로다.

## 8. 덧붙임 — 바뀐 자리를 따라 고치는 시스템 (2026-11-01, 같은 날 논의)

사용자 물음: 탐침으로 바뀐 경로나 지점을 찾았으면, 그 참조들을 바꿔 주는 시스템까지 들이면 어떤가.

### 8.1 실제로 얼마나 자주 깨지나

| 항목 | 값 (2026-10-15 이후, git) | 뜻 |
|---|---|---|
| 파일 이름 바뀜 | 12 (대부분 스킬 파일을 한 번에 옮긴 것) | 이동은 드물다 |
| 파일 삭제 | 25 | 지운 파일을 가리키던 참조가 남을 수 있다(예: `hmse.js` 삭제 → RULE-0477 변이 실패) |
| 코드 글자가 바뀌어 어긋난 참조 | 이번 세션에 1 (RULE-0526 변이 자리) | 이동보다 이쪽이 잦다 |

그래서 자동 수정보다 **바로 알려 주는 감지**의 가치가 더 크다.

### 8.2 세 등급

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| **자동으로 고침** — 현재 상태를 가리키는 기계적 참조: 저장 지도 경로 · 문서 안 링크 · 계획 `자리`의 경로 · 규칙 장부 `where`의 파일 경로(파일만 옮겨진 경우, git이 이동으로 본 것) | 뜻은 그대로고 주소만 바뀜. IDE의 이름 바꾸기와 같다 | 탐침이 고칠 목록을 만들고 장부·계획 도구로 적용 — "경로 이동 a → b" 이유를 단 사건으로 남음 | 적용 뒤 깨진 참조 0 · 링크 검사 |
| **제안만, 확인 뒤 적용** — 변이 시험의 검색 문자열(find) · `where`의 함수 이름(함수가 바뀐 경우) | 검사가 **지워져서** 문자열이 사라졌을 수도 있다. 비슷한 곳을 자동으로 다시 가리키면 없는 검사가 "잡힘"으로 계속 통과한다 — 자기 검사 장치가 스스로를 고치는 꼴(RULE-0461) | 후보를 보여 주고, "같은 검사가 맞다"는 확인이 있어야 적용. 적용하면 변이 시험을 반드시 다시 돌림 | 다시 돈 변이가 caught일 때만 장부에 기록 |
| **절대 안 고침** — 과거 기록: CHANGES 행 · 결정·계획 이력 · 영수증 · 증명 도장(발급 코드 해시) · 봉인된 장부 사건 · 데이터 | 과거에 무엇이 어디 있었는지가 기록의 목적. 도장은 코드가 바뀌면 **일부러 무효가 되게** 만든 것이라, 고치면 증명이 사라진다 | 과거 참조는 커밋에 고정해서 읽음 — 단위 장부가 이미 이 방식(`src_at` 커밋 고정) | 이 자리들에 쓰는 자동 수정은 도구가 거부 |

### 8.3 흐름

탐침이 깨진 참조를 찾음 → 사전 검사(STG-11c)가 몇 초 안에 알림 → 등급별 처리(자동 · 제안 · 거부) → 고친 것은 장부 사건으로 → 다시 검증(링크 검사 · 변이 재실행).

### 8.4 계획 반영 — 새 항목 없이 기존 둘을 넓힘

| 항목 | 덧붙인 것 |
|---|---|
| STG-11d 파일 탐침 | 깨진 참조 감지(사전 검사에 연결) + 첫 등급 자동 수정 + 셋째 등급 거부 |
| STG-11a 규칙 한 번에 | 둘째 등급 — 변이 자리가 어긋나면 후보 제안, 확인 뒤 적용, 변이 재실행 |

### 8.5 효율

이동이 드물어 자동 수정이 줄이는 호출은 많지 않다(2 주에 한두 번의 일괄 이동). 큰 효과는 감지 쪽이다. 깨진 참조로 실패하던 전체 시험(2 분 + 원인 찾기 약 5 회)이 사전 검사의 몇 초짜리 알림으로 바뀐다. §5의 추정(도구 호출 약 −30 %)에 이미 들어 있던 사전 검사 효과를 참조 깨짐까지 넓히는 정도로 본다.

|---|---|---|---|
| **세션 끊기 (STG-11f — 순서에 넣음)**: 계획 항목 하나가 끝나면 넘김 기록(`workspace/handoff/`)을 쓰고 새 세션으로. 넘김 기록에는 다음 항목 · 열린 파일 자리 · 밟은 함정만 | 대화가 길어지면 요약되고, 요약 뒤에는 구조·규약을 다시 찾아 읽는다(이번 세션도 한 번 요약됨). 읽기·찾기가 호출의 37 % | 새 세션은 넘김 기록 + 탐침(STG-11d)으로 시작 — 다시 찾는 비용이 줄어듦 | 다음 세션이 넘김 기록만으로 첫 작업 자리에 닿는지 영수증으로 확인 |
| **기록을 항목 단위로 묶기 (기록만 — 결정하지 않음)**: SCHEMA · 교과서 · CHANGES를 묶음마다가 아니라 계획 항목이 끝날 때 한 번 | 이번 ASY-08은 묶음 둘에 문서 셋을 두 번씩 씀 | 쓰는 횟수가 줄지만, "변경마다 같은 커밋에서 기록" 규약(DEC-0002 등)을 바꾸는 일이고 그동안 커밋과 문서가 잠깐 어긋남 | 열린 질문으로 남김 — 규칙 장부를 바꿀 때 사용자가 정함 |

## 10. 덧붙임 — 대화 밖으로 옮기기 (기록만 — 단계로 두지 않음, 2026-11-01)

사용자 제안: 우리가 정한 구조·절차·함정이 Claude Code 대화 메시지 안에만 있으니, Claude Code의 다른 자리로 옮기자. 사용자 결정: **적어 두되 아직 시기가 아니므로 단계로는 두지 않는다.**

### 10.1 왜 메시지 안은 나쁜가

- 사라진다: 긴 대화는 요약되고, 요약 뒤에는 장부 형식·함정을 다시 찾아 읽는다(이번 세션도 한 번 요약됨).
- 계속 비싸다: 대화에 있는 것은 매 턴 다시 읽힌다.
- 이 세션 안에서만: 클라우드 컨테이너라 개인 메모리가 남지 않는다. 남는 것은 저장소 파일뿐이다.

### 10.2 자리별로 무엇을

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| **CLAUDE.md** — 늘 참인 짧은 것만(지금처럼 장부에서 생성) | 매 턴 읽힘 | 더 넣지 않는다 | 크기 유지 |
| **Skill** — 판단이 드는 절차와 아는 함정: `/add-rule` · `/plan-change` · `/report` · `/handoff`. 도구를 부르는 얇은 층, 장부·실패 기록(영수증 · 규칙 번호)에서 생성 | 평소엔 설명 한 줄, 부를 때만 본문을 읽음. 지금 모드 skill은 "하지 말 것"뿐이고 "어떻게"는 대화에만 있음 | 절차를 다시 찾는 비용이 사라짐 | 손으로 쓴 skill은 낡으므로 생성물이어야 함 |
| **Hook** — 세션 시작·요약 직후에 지금 모드 · 다음 순서 항목 · 마지막 넘김 기록을 자동으로 넣음. 코드를 고친 직후 사전 검사를 돌려 실패만 알림 | 기억하지 않아도 기계가 함 | 안내와 검사만, 막지 않음. 문지기는 건드리지 않음 | `settings.json` 변경이라 권한 장부를 거침(RULE-0521) |
| **Subagent** — 전체 시험을 돌리고 실패 원인만, 넓은 탐색, 탐침 | 따로 떨어진 대화에서 일하고 요약만 돌려줌 | 내 대화가 작게 유지됨 | 부를 때마다 처음부터라 큰 일에만 |

### 10.3 왜 아직 아닌가

- **도구가 먼저다.** skill과 hook은 도구(STG-11a–d)를 부르는 층이다. 지금 쓰면 곧 바뀔 손 절차("명령 여섯 번")를 적게 된다.
- **구조가 아직 움직인다.** 계획·장부·측정법 틀이 이번 주에도 바뀌었다. 바뀌는 절차를 skill로 굳히면 skill을 계속 고쳐야 한다.
- **설정 변경은 무겁다.** hook은 권한 장부를 거쳐야 하고, 되돌리기도 장부 사건이다.

### 10.4 다시 꺼낼 조건 (열린 질문)

- STG-11a–d(규칙 한 번에 · 재생성 · 사전 검사 · 탐침)가 끝나고,
- 그 도구들로 하는 절차가 몇 번의 작업 동안 바뀌지 않을 때.
