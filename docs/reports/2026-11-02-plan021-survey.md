# PLAN-021 사전 조사 — 엔진의 수학 함수 호출과 JS · Rust 차이, FMA (2026-11-02)

> 목적: "정수 초월 함수 + libm 호출 0 + FMA 금지"(PLAN-021)로 JS 와 Rust 를 비트까지 맞추기 전에, 어디까지 바꿔야 하는지와 지금 얼마나 어긋나는지를 잰다. 읽기와 측정만 했고 엔진은 고치지 않았다.
> 칸: 범위 · 이유 · 영향 · 확인. 측정은 이 환경(Node 22.23, `libm` 크레이트 0.2.16, rustc 1.97.0)에서의 값이다.

## 2. JS 와 Rust 가 실제로 얼마나 다른가 (측정)

방법: 엔진이 쓰는 형태의 입력을 종류마다 30 만 개씩 만들고(Rust 쪽 임시 프로그램이 `libm::*` 결과를 16 진수로 냄), Node 의 `Math.*` 결과와 비트 단위로 비교했다. 입력 범위는 실제 쓰임을 따랐다. 임시 프로그램은 저장소에 넣지 않았다.

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| 힐 `pow(s/K, n)` (s/K 1e-6 … 1e6, n 0.5 … 8) | 수식 테이프의 점유율 | **3.00 %** 입력에서 결과가 다름, 최대 **1 ulp** | 측정 |
| 걸음 크기 `pow(err, −1/3)` (err 1e-10 … 1e3) | 걸음 갱신 | **4.41 %**, 최대 1 ulp — 걸음 크기가 1 ulp 달라지면 이후 이력이 갈라질 수 있음 | 측정 |
| 질량 작용 `pow(c, k)` (c 1e-9 … 1, k 1 … 4 정수) | 정수 지수 거듭제곱 | **2.21 %**, 최대 1 ulp. 정수 지수는 곱셈 반복으로 정확·동일하게 만들 수 있음 | 측정 |
| `log(1−U)` · `log(x)` (x 1e-9 … 1e12) | 난수·도달 | **1.97 %** · **0.25 %**, 최대 1 ulp | 측정 |
| `exp(−μ)` (μ 0 … 10) | 포아송 곱셈법 | **0 %** (30 만 개 모두 같음) | 측정 |
| 의미 | 어긋남은 항상 마지막 한 자리(1 ulp)이고 입력의 몇 퍼센트에서만 난다 | 연속 계산에서는 `rtol` 안에서 사라지지만, **걸음 수락 · 난수 수락 같은 이산 결정이 같은 입력에서 갈릴 때** 경로가 갈라진다 (앞에서 본 확률 실행 JS ≠ Rust 의 원인으로 보임. 이번에 각 호출 지점별 기여는 분리하지 않았다) | 입문 보고서 §6, 측정 |
| 환경 의존 | 결과는 Node 와 `libm` 크레이트의 구현에 달려 있다 | 런타임·라이브러리 버전이 바뀌면 이 숫자도 바뀔 수 있다 — 그래서 계산 기록부가 런타임 버전을 묶으려는 것 | PLAN-089 |

## 3. FMA (곱하고 더하기 한 번에) 확인

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| JS | ECMAScript 는 곱셈과 덧셈을 합치는 것을 허용하지 않는다 | JS 는 FMA 를 쓰지 않음 | 언어 규정 (내 지식 — 이번에 규정 원문은 열지 않음) |
| WASM (빌드 대상 `wasm32-unknown-unknown`) | 기본 켜진 기능에 `simd128` · `relaxed-simd` 가 없다 (켜진 것: bulk-memory, multivalue, mutable-globals, nontrapping-fptoint, reference-types, sign-ext) | 기본 설정에서는 FMA 가 생길 수 없음 | `rustc --print cfg --target wasm32-unknown-unknown` |
| 네이티브 (x86_64) | 기본 켜진 기능이 `fxsr` · `sse` · `sse2` 뿐이고, 만들어진 `fate_cli` 에서 `vfmadd` 류 명령을 찾아보니 **0 개** | 지금은 FMA 없음 | `objdump -d` 결과 0 |
| **보증이 없다** | 이 상태는 "기본값 덕"이다. `Cargo.toml` · `build.sh` 에 `target-cpu` · `target-feature` 설정이 없어서, 누군가 `-C target-cpu=native` 로 빌드하면 FMA 가 생길 수 있고 그러면 네이티브 = WASM 비트 일치가 조용히 깨짐 | 막는 장치가 필요: 빌드 때 명령 검사 + `-C target-feature=-fma` 명시 후보 | `Cargo.toml` · `build.sh` |

## 4. 바꿀 방법 두 가지

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| **방법 1: 직접 구현 (계획 문구 그대로)** | `pow` · `log` · `exp` 를 사칙연산만으로 한 번 쓰고(인수 줄이기 + 다항식, 계수와 연산 순서를 고정), JS 와 Rust 에 같은 순서로 옮긴다. 정수 지수는 곱셈 반복. 외부 `libm`·`Math` 호출 0 | 라이브러리·런타임 버전에 값이 안 흔들림 → 계산 기록부·논문 재현에 맞음. 수치 구현 책임을 우리가 지고, 정밀도 증명(고정밀 기준값 대조)이 필요 | PLAN-021 문구 |
| **방법 2: JS 가 Rust 의 `libm` 을 WASM 으로 부름** | 새 수치 코드 없이 두 쪽이 같은 구현을 쓴다 | 가장 싸지만, JS 기준 구현이 Rust 쪽 수학에 의존해 "서로 다른 구현이 서로를 검산한다"는 장점이 줄고, `libm` 크레이트 버전에 값이 묶임. WASM 호출 비용으로 JS 가 느려질 수 있음(측정 안 함) | 설계 판단 |
| 제 의견 | 목적이 GMP 와 논문 재현이므로 **방법 1** 을 추천 | 단계가 늘고 결과가 마지막 자리에서 바뀐다 | — |

## 5. 단계 초안 (방법 1 기준 — 사용자 확인 전)

각 단계는 별도 커밋이고, 단계마다 지문 대조(`tests/fingerprint.js`)와 전체 시험을 통과한다.

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| S1 명세와 정밀도 목표 | 쓸 함수(pow · log · exp)의 정의역(농도 1e-12 … 1e12 등), 오차 한도(지금 libm 과 같은 ≤ 1 ulp), 경계 처리(0 · 무한대 · 비수)를 문서로 고정. 정수 지수 경로와 비정수 지수 경로를 가름 | 설계 문서 한 편 | 시험 전 |
| S2 기준 구현과 정밀도 시험 (JS) | 사칙연산만으로 함수를 구현하고, 고정밀 기준값(BigInt 유리수)과 대조해 오차 ≤ 목표를 수백만 입력에서 시험. 극단 입력 포함 | 새 모듈 + 시험. 엔진 불변 | 시험 |
| S3 Rust 이식과 비트 일치 시험 | JS 와 같은 계수 · 같은 연산 순서로 옮기고, 수백만 입력에서 JS 와 비트가 같음을 시험(이번 측정 도구와 같은 방식) | 새 Rust 모듈 + 시험. 엔진 불변 | 시험 |
| S4 FMA 방지 장치 | 빌드 스크립트가 네이티브 · WASM 결과에서 FMA 명령과 SIMD 사용을 검사해 있으면 실패, `-C target-feature=-fma` 명시 | `build.sh` 변경 | `objdump` |
| S5 엔진에 교체 | 수식 테이프 · 걸음 크기 · 난수 · 도달 판정의 호출을 새 함수로 (JS · Rust 같이), WASM 다시 빌드 | **결과가 마지막 자리에서 바뀜 — 사용자 확인 필요** | 지문 대조 |
| S6 JS = Rust 비트 일치 확인 | 지문 도구에 "같은 시나리오의 JS 와 Rust 칸이 같다"는 대조를 더함. 결정론 시나리오 전부와 확률 실행에서 일치를 시도. 안 맞으면 libm 밖의 다른 원인(연산 순서 · 최대/최소 처리 등)을 칸별로 좁힘 | 이 단계의 결과가 "libm 이 유일한 원인이었나"의 답 | 지문 도구 |

## 6. 모르는 것과 위험

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| libm 이 유일한 원인인지 | JS 와 Rust 의 연산 순서가 같다는 주석을 믿고 있고, 이번에는 줄 단위로 대조하지 않았다 | S6 에서 맞지 않으면 다른 원인을 찾는 단계가 추가됨 | 해부 1호 §0 |
| 정의역 밖 입력 | 힐 n ≳ 100 에서 넘침을 사법부가 막고 있음. 새 함수도 같은 경계에서 같은 결과(무한대)를 내야 사법부 판정이 안 바뀜 | S1 에서 경계 처리 명시 | 교과서 4.9F |
| 정수 지수 곱셈 반복 | 지수가 큰 정수(예: 힐 n = 8)에서 곱셈 반복은 오차가 커질 수 있음 | 지수 크기에 따라 곱셈 반복과 exp/log 경로를 나누는 기준이 필요 | S1 |
| 성능 | 직접 구현이 `Math.pow` · `libm::pow` 보다 느릴 수 있다 | JS 는 수식 평가가 느려질 수 있음. 측정은 S5 에서 | 측정 필요 |
| 결과 변화의 크기 | 마지막 자리 차이가 걸음 이력을 바꿔 도달·결정 시각이 `event_tol`(0.01 s) · `commitment_tol`(1 s) 안에서 움직일 수 있음 | 지문 도구로 어디가 바뀌는지 확인, 시험의 허용 오차 안인지 확인 | S5 |
