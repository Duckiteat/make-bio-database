## 1. 이 제안서가 막는 것과 못 막는 것

| 질문 | 판단 | 근거 | 의미 |
|---|---|---|---|
| 철학(2장)과 네 영역(3장)이 맞는 방향인가 | 맞다. 3.2 "개발 AI 가 닿는 권한으로 통제 영역을 바꿀 수 있으면 독립이 아니다" 는 재검토 결론과 같다 | N8–N10 은 같은 원인 — 검사 코드 · 워크플로 · 의존 파일 · '선언 없음 = 사람' 가정이 AI 가 쓸 수 있는 자리 | 최종 정의의 뼈대로 쓸 만함 |
| 지금 독립 영역을 만들 수 있나 | 지금 구조로는 못 만든다 | AI 의 push · CI 실행 · PR 이 모두 같은 GitHub 계정(Duckiteat)으로 남음(조회). 그 계정이 관리하는 통제 영역은 AI 도 그 토큰으로 닿음 | 가장 큰 지렛대 = 신원 분리(AI 전용 계정 또는 GitHub App · 승인과 설정은 사람 계정만). 이것 없이는 C · D 영역이 이름뿐 |

## 2. N8–N12 를 구조로 막는 가장 작은 길 (제안서 2 · 3 단계)

| 경로 | 구조적 해결 | 비용 | 새로 생길 수 있는 틈 |
|---|---|---|---|
| C6 · D2 (워크플로를 PR 이 바꿈) | 판정 워크플로를 `pull_request_target` 으로 — 워크플로 · 판정 코드는 main 에서, PR 은 데이터로만 | 작음 — 워크플로 하나, 비밀 값 필요 없음 | PR 코드를 실행하면 위험 — git 객체만 읽고 권한은 읽기만 |
| N9 (병합 커밋) | 커밋마다에 더해 base..head 전체 차이도 판정(병합 커밋은 첫 부모와) | 작음 | 거의 없음 |
| N10 (의존 파일) | 결정하는 판정은 모두 main 트리에서만 — 브랜치의 의존 파일은 상관없음 | 작음(위와 함께) | main 에 들어가는 백도어는 PR 검토만 → 신원 분리 |
| N8 ('선언 없음 = 사람') | 영수증 대신 서명으로 — 사람 커밋은 사용자 기기의 서명 키, 그 밖은 AI | 중간 — 사용자 기기에 서명 키 | 키를 AI 가 닿는 곳(Codespaces 등)에 두면 무너짐 |
| N11 (fail-open) | 문지기 오류 시 쓰는 도구를 막음(fail-closed) — 제안서 8.2 | 작음(L6 묶음) | 문지기 버그가 작업을 멈춤 |
| N12 · 병합 주체 | AI 계정 분리 + main 규칙: 사람 계정(CODEOWNERS) 승인 1 필수 · 자동 병합 끄기 | 중간 — 계정 · 설정 | 사람이 diff 를 안 읽고 누르면 못 막음(제안서 4.1 책임 영역) |
