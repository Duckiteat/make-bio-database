> 틀: 엔진을 부분으로 가르고, 부분마다 (1) 무엇을 하는지 (2) 그 개념이 어디서 끊기는지를 적는다. 칭찬을 빼고 한계와 모순만 적되, 마지막에 단단한 곳도 한 표로 적어 둔다.
> 칸: 범위 · 이유(문제) · 영향 · 확인(근거). 확인 칸의 `파일:줄` 은 이번에 직접 읽은 곳이고, `측정`은 이번 세션에서 스크립트로 잰 값이다.
> 등급: **치명** = 결론이 틀릴 수 있음 · **중대** = 조건에 따라 틀리거나 막힘 · **경미** = 비용·가독성.
> 앞선 보고서(`2026-10-25-architecture-analysis.md`)와 겹치는 항목은 거기를 가리키고, 이번에 새로 찾은 것에는 **신규**를 붙인다.

## 2. 시간 측정 — 엔진이 시간을 세는 방법 일곱 가지

시간은 한 정의로 세지지 않는다. 엔진마다·층마다 서로 다른 시계를 쓰고, 그 사이를 임시 허용치로 잇는다.

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| **K1 속도 엔진 시계**: `t = +(i·dt).toFixed(9)`, 걸음 수 `ceil(t_end/dt)` (등급 **중대**, 신규) | 곱셈이라 누적 오차는 없지만, `t_end` 가 `dt` 의 배수가 아니면 마지막 걸음이 `t_end` 를 넘고 그대로 돈다. `toFixed(9)` 는 dt 가 1e-9 규모에 닿으면 시각이 겹친다. | `t_end=5, dt=0.07` 이면 5.04 까지, `t_end=100, dt=0.3` 이면 100.2 까지 시뮬레이션함. 요청한 시간보다 길게 돈 결과가 `t_end` 로 보고됨 | `core.js:598·639`, **측정**: 72 걸음 → 끝 5.04 / 334 걸음 → 끝 100.2 |
| **K2 운명 엔진 시계**: 관찰 격자를 `t += dt` 로 누적, 끝 판정 `t < t1 - 1e-9` (등급 **중대**, 신규) | 부동소수 덧셈 오차가 쌓이고, 허용치 1e-9 는 임의의 값이다. 기본 dt=60 은 2진 정확이라 지금은 안 드러난다. | dt 가 0.1 같은 비정확 값이면 격자가 표류함(0.1 을 1e6 번 더하면 오차 1.3e-6). JS·Rust 가 같은 누적을 해서 둘은 서로 일치하지만 참 격자와는 어긋남 | `fate_engine.js:335`, `engine.rs:161·468`, **측정** |
| **K3 기록 시각이 실제 적분 끝과 다름** (등급 **중대**, 신규) | 마지막 구간이 dt 보다 짧을 때 적분은 `te = t1` 까지만 가는데 기록 시각·스냅숏·고갈/재생 사건 시각은 `t + dt` 를 쓴다 | `t_end=100, dt=60` 이면 상태는 t=100 인데 기록은 t=120. 마지막 점의 시각이 틀리고 그 점에서 감지한 사건·도달 시각도 틀림. JS 와 Rust 가 같은 오류를 같게 냄 | `fate_engine.js:347·349`, `engine.rs:471·486`, **측정**: `{적분끝 100, 기록 t 120}` |
| **K4 신호는 격자점에서만 바뀜** (등급 **중대**; 앞 보고서는 경미로 적음) | `signalAt` 이 `e.t ≤ t + 1e-9` 인 마지막 값을 쓰고 격자점마다 한 번만 부른다. 신호 시각이 격자 사이면 다음 격자점에서 적용된다 | 신호가 100 s 에 켜지면 120 s 에 켜짐(**측정**: 지연 20 s, 최악 dt−ε). 결정 탐침은 "신호를 끊은 시각" 을 물으므로 결정 시각의 체계적 편향 원천. 신호 시간표를 격자보다 촘촘히 줄 수 없음 | `fate_engine.js:312`, `engine.rs:449–455`, **측정** |
| **K5 내부 걸음 h 는 가변이고 실행마다 처음부터** (등급 **경미**) | 적분기 안 걸음은 오차 제어로 정하지만, `run` 마다 `h = h0 = 1 s` 로 되돌린다(탐침·`advance` 호출마다). 안 쌓이는 상태 정보 | 본 실행에서 이미 알아낸 적절한 h 를 탐침이 버리고 ×5 씩 키우며 다시 올라감 → 낭비. 또 `advance(P→c)` 의 걸음 분할이 본 실행과 달라 상태가 rtol 수준에서만 같음 | `fate_engine.js:319`, `engine.rs:461` |
| **K6 확률 층의 두 시계**: 적분 시각 t 와 규칙별 내부 시각 T(적분 성향) (등급 **중대**, 신규) | SSA 는 T 가 다음 발화 P 에 닿는 지점을 근 찾기(`ssa_tol` 1e-9, 최대 100회)로 찾는다. 그 결과가 걸음 길이를 줄이고, 줄어든 걸음이 거부·h 갱신에 다시 영향을 준다 | 발화 시각이 정확하지만, 걸음 수·거부 수·난수 소비가 분할·허용 오차에 얽혀 같은 seed 라도 설정이 바뀌면 경로가 달라짐 | `fate_engine.js:250–262`, `coupling.js:28` |
| **K7 벽시계 시간이 판정 입력에 섞임** (등급 **중대**, 신규, 판정 쪽 사용처는 **미확인**) | 조정자의 `timed` 가 `process.hrtime` 으로 잰 `ms`·`refMs` 를 비교 결과에 싣는다. `compare.js` 가 `dMs` 를 계산한다 | 실행 시간은 기계·부하에 따라 달라서, 판정 입력에 들어가면 같은 입력이 다른 판정을 낼 수 있다. 어디까지 쓰이는지는 `compare.js:39` 뒤를 읽지 않았다 | `orchestrator.js:54`, `judicial/compare.js:21·39` |

### 2.1 시간에 관한 개념 한계 (K1–K7 밑에 깔린 것)

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| **시각의 종류가 섞임**: 물리 시각(초) · 관찰 격자 시각 · 적분 걸음의 누적 시각 · 확률 내부 시각 T | 한 단위(초)를 쓰지만 서로 다른 정밀도를 갖고, 변환 규칙이 코드 곳곳에 흩어져 있다 | 어느 시각이 "참" 인지 정의가 없음. 시각을 비교하거나 다른 엔진 결과와 대조할 때마다 허용치를 임의로 둠 | K1–K6 |
| **허용치 1e-9, 1e-6, 1e-12 가 곳곳에** | 같은 목적(시각 비교)에 서로 다른 임의 상수: 끝 판정 1e-9 · 신호 1e-9 · `snapAt` 1e-6 · SSA 근 찾기 `1e-12·max(1,tt)` | 한 곳만 고치면 다른 곳과 어긋남 | `fate_engine.js:335·312·399·254`, `engine.rs:161·452·468·408` |
| **시간 척도 선언이 없음** | 빠른 단계(속도 상수 없는 "즉시")의 시간 척도가 `dt` 가 됨(§3 E2). 시나리오는 무엇을 "빠른 극한" 으로 두는지 선언하지 못함 | `dt` 를 바꾸는 것이 생물 가정을 바꾸는 것(앞 보고서 D4 중대와 같음) | `core.js:646–652`, PLAN-080 |
| **단위가 변수명·주석에만 있음** | 초, 분자 수, 몰 농도가 숫자 하나로 오감. ASY-08 의 차원 검사(RULE-0526)는 속도 법칙에만 걸리고 시간 축·결합점에는 아직 안 걸림 | 단위 오류가 조용히 통과 | `coupling.js`(단위는 `unit` 칸 문자열) |

## 3. 부분별 한계

### E1 사건 기반 `simulate`

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| **선언 순서 의존** (중대, 앞 보고서 D3) | 라운드마다 단계를 목록 순서대로 발화, 같은 입력을 다투면 앞 단계가 먼저 가져감 | 경쟁 경로 결과가 파일 순서로 정해짐 | `core.js:364–378` |
| **"시간" 이 없음** (설계) | 라운드는 시간이 아니라 순서다. `rounds: 60` 은 임의 상한 | 도달 여부만 말할 수 있고 속도·순서 간 경쟁은 말할 수 없음. 사용자가 라운드 수를 시간처럼 읽으면 오해 | `core.js:277·361` |
| **시작량 기본값이 결론에 들어감** (중대) | 데이터에도 지정에도 없으면 `amount=10`, `bulk=1000` 분자. 순환에서 막힌 단계는 "가장 상류·특징이 가장 적은 묶음 하나" 를 보충(`cycleSeeds`) | 도달 결과가 사실이 아닌 휴리스틱에 의존. 보충한 묶음이 보고되기는 함 | `core.js:277·326·342–357` |
| **`k = min(행위자 수, 입력/화학량)` 발화** | 효소가 한 라운드에 자기 수만큼 촉매한다고 가정(회전율 무한) | 효소 개수가 많으면 한 라운드에 전부 소진됨 | `core.js:369–371` |

### E2 속도 기반 `simulateRate`

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| **명시 오일러 + 가용량 자르기** (중대, 앞 D4) | 오차 추정·걸음 거부 없음. 자르기는 입력이 모자라면 ξ 를 줄일 뿐, 질량 보존만 지키고 동역학은 왜곡 | Δt 에 따라 끝 값이 바뀜(LPS 끝 값 상대 6.5e-5) | `core.js:662·666–668` |
| **단계 안 순차 갱신** (중대, 앞 D4) | 반응 단계가 IR 순서로 바로 N 을 고쳐 뒤 단계가 앞 단계 결과를 읽음 → 공급 → 분해 순서 | 분할 오차 + 순서 의존 | `core.js:639–720` |
| **"즉시" 단계의 시간 척도 = Δt** (중대, 앞 D4) | 속도 상수 없는 단계는 가용량 전부를 한 걸음에 | 속도 단계와 섞이면 Δt 를 바꾸는 것이 가정을 바꿈 | `core.js:646–652` |
| **미카엘리스–멘텐이 첫 기질만** (중대, 앞 D2) | `s0 = lawIns[0]`. 기질이 없으면 `s0 = 1`(농도 1 M 로 가정) → 포화 항 `1/(Km+1)` | **신규 세부**: 법칙 입력이 비면 농도 1 M 이라는 근거 없는 값이 속도에 들어감 | `core.js:661` |
| **확률 층이 분해에만 있음** (중대, **신규**) | `stochastic` 이면 이항 추출은 분해 규칙(③)에만 쓰인다. 반응·공급은 결정론 오일러 | "확률 실행" 이라고 불러도 반응의 요동은 없음. 분해만 요동치는 반쪽 모형인데 이 사실이 결과 필드에 드러나지 않음 | `core.js:708–711` |
| **이항 추출의 근사** (경미–중대, **신규**) | n ≤ 60 은 베르누이 n 번, n > 60 은 정규 근사(Box–Muller) 후 반올림·0 이하 자르기. 정규 근사는 `n·p` 가 작을 때 편향이 있고 `Math.log/cos` 를 씀 | 평균 보존이 깨질 수 있음(크기는 이번에 안 쟀다). JS 만 쓰므로 Rust 와 대조 대상은 아님 | `core.js:423–429` |
| **두 번째 난수 생성기** (경미, **신규**) | 속도 엔진은 mulberry32, 운명 엔진은 xoshiro256++. 시드 의미·궤적 번호 규칙이 다름 | PLAN-020(카운터 난수)을 하면 둘을 하나로 만들어야 함. 지금은 "같은 seed" 가 엔진 사이에서 다른 뜻 | `core.js:422`, `rng.js` |
| **정지 판정이 Δt 격자에 묶임** (중대, **신규**) | 창 `winN = round(window/dt)` 걸음, 도달·고갈·재생 시각도 걸음 해상도. `peak.rate × winN × dt ≥ 1` 같은 임의 문턱 | 정지 시각의 해상도 = dt. `dt` 를 바꾸면 정지 여부가 바뀔 수 있음(재현 확인은 안 함) | `core.js:731–746` |

| **질량 원장은 닫혀 있으나 시간 원장은 없음** | 질량·부분 구조는 double-double 로 1e-14 까지 감사. 시각에는 비슷한 장부가 없다 | 시각 오차(K1–K4)는 어떤 감사도 못 잡고 있음 | `fate_engine.js:65–89` |
| **기준해가 독립이 아님** | 같은 코드의 촘촘한 실행 / 다른 엔진(같은 IR) | 코드 자체 오류(개념 오류)를 잡으려면 해석해·외부 모음(DSMTS 등)이 필요 — PLAN-088 | `orchestrator.js:63`, PLAN-088 |
