# 계산 기록부 설계 초안 — 실행 하나하나를 재현·감사할 수 있게 (2026-11-02)

> 목적: 목표가 GMP 활용 수준이므로, 엔진이 낸 결과마다 "어떤 입력·코드·설정·환경에서 어떻게 나왔는지"를 남기고 나중에 다시 확인할 수 있게 한다. 이 문서는 **설계 초안**이다. 코드·장부·계획은 고치지 않았다.
> GMP 해석: 이 문서는 일반적인 데이터 완전성 원칙(누가·언제·무엇을·원본·정확·완전·일관·지속·접근 가능)을 길잡이로만 쓴다. 규정 적합성 판단은 품질 담당이 한다. 어떤 규정·절차를 기준으로 삼는지는 §7 에서 사용자에게 묻는다.
> 칸: 범위 · 이유(문제) · 영향 · 확인.

## 2. 기록부 한 줄에 담을 항목 (안)

기록부는 실행 하나가 끝날 때 한 줄을 덧붙이는 추가 전용 파일(안: `data/runs.jsonl`)이다. 줄마다 `prev`·`root` 로 사슬을 이어 중간 수정이 들통나게 한다(사전 등록부와 같은 틀).

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| 번호·시각·주체 | 누가(`BIODB_ROLE`·모드)·언제 돌렸나 | 시각은 **기록용이고 판정에 쓰지 않는다**(K7 의 교훈). 사슬 `seq`·`prev`·`root` | `dbtool.mjs:635` |
| 입력 정체 | 어떤 데이터·시나리오·IR 로 돌렸나 | db sha256 · 시나리오 sha256(가정 번호를 푼 정준형) · IR 해시 · 사전 등록 번호(있으면) | `clerk.mjs:141`, `fate_audit.js:45` |
| 설정 | 허용 오차·문턱 등 결과를 바꾸는 수치 | 결합점 전체 값과 `_source` · 시나리오의 `dt_slow`·`t_end`·`stochastic{seed}` · 궤적 번호 | `coupling.js` |
| 코드 정체 | 어떤 코드가 계산했나 | git 커밋 + **작업 트리가 깨끗한지** + 엔진·컴파일러·`core.js`·`model.js` 파일 해시 + WASM 해시(`wasm_sha256`)와 소스 해시 + `rustc` | `fate_core.wasm.json` |
| 실행 환경 | 같은 코드도 환경에 따라 끝자리가 다를 수 있다 | Node 버전 · 백엔드(`js`/`rust`/네이티브) · 탐침 lanes · 플랫폼 이름. **환경 변수 전체는 기록하지 않는다**(비밀 혼입 방지, RULE-0518) | 1호 E7 |
| 시계 정보 | 시각 결함을 나중에 찾을 수 있게 | 요청한 `t_end` · 실제로 적분한 마지막 시각 · 마지막 기록 시각 · 둘이 다르면 표시(K1·K3 탐지) | 1호 §2 |
| 출력 정체 | 결과가 같은지 비교 | 정준화한 출력(궤적·최종 상태·사건·결정 시각)의 해시 + 적분 요약(걸음·거부·`hMinHits`) | `fate_engine.js:453–` |
| 판정 연결 | 계산과 판단을 이어 준다 | 그 실행을 판정한 사법부 결과(감사 코드)와 도장 번호(있으면) | `attestation.js` |
| 진단 값 | 실행 시간 같은 환경 의존 값 | **해시와 판정에서 제외한 별도 칸**(`diagnostic`)에만 적는다. 기록은 하되 판정에 못 쓰게 구조로 막는다 | `compare.js:39`(문제 사례) |

## 3. 어디서 조립하고 누가 쓰나

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| 엔진은 기록을 만들지 않는다 | 엔진은 순수 함수여야 한다(파일 쓰기·시계 읽기 금지) | 엔진 코드는 안 바뀐다. 코드 정체 등은 엔진 밖에서 모은다 | `tripartite-governance.md` §0 |
| 조정자가 기록 한 줄을 조립한다 | 조정자는 행정 실행과 사법 판정 사이의 배선이다 | `orchestrator.js` 의 실행 함수(`runFate` 등)가 결과를 만든 뒤 기록 내용을 모은다 | `orchestrator.js:40–` |
| 서기가 쓴다 | 쓰기는 서기뿐이다 | `registry` 구역 허용 목록에 기록부 파일을 더하고, 쓰기 조건은 "사법부 검사 통과"로 한다 | `clerk.mjs:39` |
| 사법부가 기록부를 검사한다 | 기록이 빠졌거나 고쳐졌는지 독립적으로 본다 | 사슬 재생 검사(`log_audit.js` 와 같은 틀) + **재현 검사**: 기록의 입력으로 다시 돌려 출력 해시를 대조 | `judicial/log_audit.js` |
| 재현 검사의 범위 | 같은 코드·백엔드면 비트 단위로 같아야 한다 | 같은 WASM·같은 백엔드끼리는 정확히 비교. **JS 대 Rust 는 지금 `rtol` 안에서만 같으므로 정확 비교가 불가능**(PLAN-021 이전) | 1호 E7 |

## 5. 한계와 위험

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| 엔진 결정론이 먼저 | 출력 해시 비교는 같은 입력이 같은 출력을 낼 때만 의미가 있다 | 확률 실행의 시드 표류(PLAN-020), 벽시계 입력(K7), 시계 결함(K1·K3·K4)이 정리되기 전에는 재현 검사가 가짜 실패를 낼 수 있다 | 1호 §2, 2호 §3 |
| 작업 트리가 더러운 실행 | 커밋되지 않은 변경으로 돌린 결과는 커밋 해시로 재현할 수 없다 | 코드 파일 해시를 함께 기록하고 "깨끗하지 않음" 표시를 남긴다. GMP 용도 실행은 깨끗한 상태만 허용하는 규칙이 필요할 수 있다 | §7 |
| 기록 양 | 실행마다 한 줄이면 탐색 중 실행이 수천 줄이 된다 | **정식 실행(보고·검증용)만 기록**하는 구분이 필요하다 | §7 |
| 시각의 이중성 | 기록부 시각(벽시계)과 시뮬레이션 시각(초)이 다른 개념 | 열 이름을 분리한다(`recorded_at` 대 `sim.t_end` 등) | 1호 §2.1 |
| 비밀 | 환경 정보 수집 중 토큰이 섞일 수 있다 | 버전 문자열·플랫폼 이름만 수집한다. 환경 변수·경로의 홈 디렉터리는 수집하지 않는다 | `RULE-0518` |
| 이중 기록 | 영수증(개발 과정)과 기록부(계산 과정)가 둘 다 있다 | 목적이 다르다: 영수증은 "누가 무엇을 바꿨나", 기록부는 "무엇이 어떻게 계산됐나". 서로를 가리키는 칸(영수증 이름)을 기록부에 넣을지는 열린 질문 | §7 |

## 6. 단계 제안

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| R0 코드 정체 | 엔진과 무관하게 먼저 가능한 일: 실행 결과에 코드·WASM·환경 정체를 묶는다 | 결과가 바뀌지 않는다(주변 정보만 추가). 비트 연속성 영향 없음 | §2 |
| R1 기록부 줄 쓰기 | 서기 구역에 기록부를 더하고 조정자가 조립한다 | 입법·조정 코드 변경 | §3·§4 |
| R2 기록부 검사 | 사슬 재생 + 필수 칸 검사 + 진단 값 분리 확인 | 사법부 새 모듈 | §3 |
| R3 재현 검사 | 기록의 입력으로 다시 돌려 출력 해시를 대조 | **안전망 시험(PLAN-088)·시계 정리·난수(PLAN-020)·초월 함수(PLAN-021)가 끝난 뒤** 의미가 있다 | §5 |
| 앞선 순서와의 관계 | 안전망 시험 → 시계 정리는 그대로 두고, R0 는 그 앞에 끼울 수 있다 | 순서를 바꾸는 이유를 `plan.mjs apply` 로 기록해야 한다 | 입문 보고서 §10 |
