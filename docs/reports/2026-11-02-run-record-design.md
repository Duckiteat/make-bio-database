# 계산 기록부 설계 초안 — 실행 하나하나를 재현·감사할 수 있게 (2026-11-02)

> 목적: 목표가 GMP 활용 수준이므로, 엔진이 낸 결과마다 "어떤 입력·코드·설정·환경에서 어떻게 나왔는지"를 남기고 나중에 다시 확인할 수 있게 한다. 이 문서는 **설계 초안**이다. 코드·장부·계획은 고치지 않았다.
> GMP 해석: 이 문서는 일반적인 데이터 완전성 원칙(누가·언제·무엇을·원본·정확·완전·일관·지속·접근 가능)을 길잡이로만 쓴다. 규정 적합성 판단은 품질 담당이 한다. 어떤 규정·절차를 기준으로 삼는지는 §7 에서 사용자에게 묻는다.
> 칸: 범위 · 이유(문제) · 영향 · 확인.

## 2. 기록부 한 줄에 담을 항목 (안)

기록부는 실행 하나가 끝날 때 한 줄을 덧붙이는 추가 전용 파일(안: `data/runs.jsonl`)이다. 줄마다 `prev`·`root` 로 사슬을 이어 중간 수정이 들통나게 한다(사전 등록부와 같은 틀).

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| 번호·시각·주체 | 누가(`BIODB_ROLE`·모드)·언제 돌렸나 | 시각은 **기록용이고 판정에 쓰지 않는다**(K7 의 교훈). 사슬 `seq`·`prev`·`root` | `dbtool.mjs:635` |
| 입력 정체 | 어떤 데이터·시나리오·IR 로 돌렸나 | db sha256 · 시나리오 sha256(가정 번호를 푼 정준형) · IR 해시 · 사전 등록 번호(있으면) | `clerk.mjs:141`, `fate_audit.js:45` |
| 설정 | 허용 오차·문턱 등 결과를 바꾸는 수치 | 결합점 전체 값과 `_source` · 시나리오의 `dt_slow`·`t_end`·`stochastic{seed}` · 궤적 번호 | `coupling.js` |
| 코드 정체 | 어떤 코드가 계산했나 | git 커밋 + **작업 트리가 깨끗한지** + 엔진·컴파일러·`core.js`·`model.js` 파일 해시 + WASM 해시(`wasm_sha256`)와 소스 해시 + `rustc` | `fate_core.wasm.json` |
| 실행 환경 | 같은 코드도 환경에 따라 끝자리가 다를 수 있다 | Node 버전 · 백엔드(`js`/`rust`/네이티브) · 탐침 lanes · 플랫폼 이름. **환경 변수 전체는 기록하지 않는다**(비밀 혼입 방지, RULE-0518) | 1호 E7 |
| 시계 정보 | 시각 결함을 나중에 찾을 수 있게 | 요청한 `t_end` · 실제로 적분한 마지막 시각 · 마지막 기록 시각 · 둘이 다르면 표시(K1·K3 탐지) | 1호 §2 |
| 출력 정체 | 결과가 같은지 비교 | 정준화한 출력(궤적·최종 상태·사건·결정 시각)의 해시 + 적분 요약(걸음·거부·`hMinHits`) | `fate_engine.js:453–` |
| 판정 연결 | 계산과 판단을 이어 준다 | 그 실행을 판정한 사법부 결과(감사 코드)와 도장 번호(있으면) | `attestation.js` |
| 진단 값 | 실행 시간 같은 환경 의존 값 | **해시와 판정에서 제외한 별도 칸**(`diagnostic`)에만 적는다. 기록은 하되 판정에 못 쓰게 구조로 막는다 | `compare.js:39`(문제 사례) |

## 3. 어디서 조립하고 누가 쓰나

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| 엔진은 기록을 만들지 않는다 | 엔진은 순수 함수여야 한다(파일 쓰기·시계 읽기 금지) | 엔진 코드는 안 바뀐다. 코드 정체 등은 엔진 밖에서 모은다 | `tripartite-governance.md` §0 |
| 조정자가 기록 한 줄을 조립한다 | 조정자는 행정 실행과 사법 판정 사이의 배선이다 | `orchestrator.js` 의 실행 함수(`runFate` 등)가 결과를 만든 뒤 기록 내용을 모은다 | `orchestrator.js:40–` |
| 서기가 쓴다 | 쓰기는 서기뿐이다 | `registry` 구역 허용 목록에 기록부 파일을 더하고, 쓰기 조건은 "사법부 검사 통과"로 한다 | `clerk.mjs:39` |
| 사법부가 기록부를 검사한다 | 기록이 빠졌거나 고쳐졌는지 독립적으로 본다 | 사슬 재생 검사(`log_audit.js` 와 같은 틀) + **재현 검사**: 기록의 입력으로 다시 돌려 출력 해시를 대조 | `judicial/log_audit.js` |
| 재현 검사의 범위 | 같은 코드·백엔드면 비트 단위로 같아야 한다 | 같은 WASM·같은 백엔드끼리는 정확히 비교. **JS 대 Rust 는 지금 `rtol` 안에서만 같으므로 정확 비교가 불가능**(PLAN-021 이전) | 1호 E7 |

## 5. 한계와 위험

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| 엔진 결정론이 먼저 | 출력 해시 비교는 같은 입력이 같은 출력을 낼 때만 의미가 있다 | 확률 실행의 시드 표류(PLAN-020), 벽시계 입력(K7), 시계 결함(K1·K3·K4)이 정리되기 전에는 재현 검사가 가짜 실패를 낼 수 있다 | 1호 §2, 2호 §3 |
| 작업 트리가 더러운 실행 | 커밋되지 않은 변경으로 돌린 결과는 커밋 해시로 재현할 수 없다 | 코드 파일 해시를 함께 기록하고 "깨끗하지 않음" 표시를 남긴다. GMP 용도 실행은 깨끗한 상태만 허용하는 규칙이 필요할 수 있다 | §7 |
| 기록 양 | 실행마다 한 줄이면 탐색 중 실행이 수천 줄이 된다 | **정식 실행(보고·검증용)만 기록**하는 구분이 필요하다 | §7 |
| 시각의 이중성 | 기록부 시각(벽시계)과 시뮬레이션 시각(초)이 다른 개념 | 열 이름을 분리한다(`recorded_at` 대 `sim.t_end` 등) | 1호 §2.1 |
| 비밀 | 환경 정보 수집 중 토큰이 섞일 수 있다 | 버전 문자열·플랫폼 이름만 수집한다. 환경 변수·경로의 홈 디렉터리는 수집하지 않는다 | `RULE-0518` |
| 이중 기록 | 영수증(개발 과정)과 기록부(계산 과정)가 둘 다 있다 | 목적이 다르다: 영수증은 "누가 무엇을 바꿨나", 기록부는 "무엇이 어떻게 계산됐나". 서로를 가리키는 칸(영수증 이름)을 기록부에 넣을지는 열린 질문 | §7 |

## 8. 논의 — 기록의 쓸모는 재현에서 끝나지 않고 보고서·논문의 기준이 되는 데까지 (사용자 제기)

> 제기: 계산 기록부의 활용은 실험 재현에서 끝나지 않고, 보고서나 논문을 쓰는 기준으로 존재해야 한다. 이 절은 그 지점의 논의이고 결정은 아직 없다.

### 8.1 논문이 기록에 요구하는 것

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| 주장 단위 추적 | 논문의 문장·그림·표의 숫자 하나가 "어느 실행의 어느 출력인지" 거슬러 갈 수 있어야 한다 | 기록부 줄(실행 단위)만으로는 부족하고, 주장과 실행을 잇는 연결이 필요하다 | §8.3 |
| 방법의 완전성 | 독자가 같은 입력·코드·설정으로 다시 돌릴 수 있어야 한다 | 계산 기록부의 입력·코드·설정·환경 칸이 그대로 방법 절의 재료가 된다 | §2 |
| 탐색과 확인의 구분 | 사전 등록 없이 본 결과를 확증처럼 쓰면 안 된다 | 이미 있다: 규약 없는 실행은 "탐색 실행"이라 검증 결론을 못 낸다 | `protocol.js` 머리 |
| 가정 의존의 노출 | 속도 상수 대부분이 가상 값이면 결론은 "그 가정 아래에서"만 성립한다 | 시나리오 44 개 중 43 개가 가상이고 데이터 실측 상수는 4 개다(입문 보고서 §5). 논문이 이를 과장하지 못하게 구조로 드러내야 한다 | 입문 보고서 §5 |
| 실패와 막다른 길의 공개 | 부정 결과·거부된 실행이 빠지면 선택적 보고가 된다 | 증거·방법 보고서가 "실패·막다른 길을 숨기지 않는다"를 설계 목표로 이미 적었다 | `evidence_report.js` 머리 |
| 시점의 고정 | 논문이 인용한 상태를 나중에 그대로 불러올 수 있어야 한다 | 커밋 해시 + 기록부 사슬의 `root` 를 한 쌍으로 인용 가능한 봉인으로 삼을 수 있다 | §8.3 |
| 작성 과정의 공개 | AI 도구를 쓴 작업은 학술지·기관이 사용 공개를 요구하는 경우가 있다(정책은 곳마다 다르므로 확인 필요) | 개발 과정 기록(영수증)이 여기서 쓰임이 생긴다. 앞서 "읽기·대화 기록은 필요 없다"고 한 판단은 계산 과정에 한정한 것이다 | 입문 보고서의 영수증 논의 |

### 8.2 이미 있는 것 (직접 확인)

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| 독자가 논문·전문가인 보고서 | 증거·방법 보고서는 "한 사람이 이것 하나를 읽고 결론을 완전히 이해하고 질문할 수 있어야 한다"를 목표로 하고, 사고 패턴의 지문(등급·닫는 방법·등록된 한계·반증 가능 판정)과 "얻은 것·다음 지점·바닥의 불안정함"을 쓴다 | 논문 쪽 출력의 뼈대가 있다 | `judicial/evidence_report.js:1–7` |
| 과정 분석 보고서 | 요약 · 단계별 전개 · 무결성 증명서 · 인과 추적 · 기술 부록. 증명서가 부분 구조 원장(≤ 1e-14) · 저장소 재생 · 선언된 신호 일정 일치 · 결정론(다시 돌려 같은 궤적 해시) · 입력 해시와 매개변수 출처를 판정 | 실행 한 번의 완전한 서술. 다만 코드 정체·환경은 없다(§1) | `judicial/process_report.js:1–7` |
| 모의 실험 규약 | 실제 실험과 같은 실험을 모델에서 했을 때 같은 결과인가를 묻는다. 대응 실험의 출처(DOI·PMID), 음성 대조, 반복 수(검정력 계산), 검증 세트와 추정 세트의 분리, 사전 등록 | 논문 방법 절이 요구하는 내용의 큰 부분이 이미 구조화돼 있다 | `judicial/protocol.js:1–30` |
| 보고서 출력 | `fate --report`, `evidence --report` 로 파일을 만든다 | 출력은 있으나 기록부(실행 계보)와는 연결돼 있지 않다 | `dbtool.mjs:38·534` |

### 8.3 빈 곳과 아이디어 (초안, 결정 아님)

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| 보고서가 기록부를 가리키지 않음 | 보고서는 실행 직후 만들어지고 실행의 정체(코드·환경)가 안 들어간다 | 보고서 머리에 "기록부 번호 + 사슬 root" 를 필수로 박으면 논문의 어떤 숫자든 기록부로 되짚을 수 있다 | §2 |
| 주장 장부(안) | 논문의 주장 하나마다 `{ 주장 번호, 문장, 근거 실행 번호들, 근거 관찰(DOI), 도장 번호, 가정 의존 표시 }` 를 추가 전용 장부로 남긴다 | "이 문장은 어느 실행에서 나왔나"가 구조로 답해진다. 근거 없는 주장은 장부에 못 올린다 | 새 기능 |
| 숫자를 손으로 옮기지 않기 | 보고서·논문의 숫자를 사람이 타이핑하면 옮겨 적다 틀린다. `RULE-0215`(같은 문구를 복사하지 않는다)와 같은 취지다 | 방법 절·결과 표를 기록부에서 생성하고, 사람이 쓰는 것은 해석 문장으로 한정한다 | `RULE-0215` |
| 가정 의존 표시를 출력에 강제 | 가상 시나리오 결과가 확증처럼 읽히지 않게 | 가상 상수를 쓴 실행은 보고서 머리에 자동으로 "가정 의존: 가상 상수 N 개 / 실측 M 개"를 쓰고, 해당 등급 아래에서는 "일치" 같은 결론 단어를 못 쓰게 한다. 등급 관문(`min_grade`)이 이미 비슷한 장치를 갖고 있다 | 입문 보고서 §5, `core.js:760` |
| 내보내기 묶음 | 제출·감사 때 필요한 것을 한 꾸러미로 | 데이터베이스 해시 · 시나리오 · 기록부 해당 구간 · 보고서 · 도장 · 코드 커밋과 WASM 해시를 한 디렉터리로 내보내고 묶음 전체의 해시를 인용한다. 시뮬레이션 실험의 표준 교환 형식을 쓸지는 조사가 필요하다 | 조사 필요 |
| 일반적으로 참고할 틀(조사 필요) | 계산 모델 신뢰성 평가와 시뮬레이션 실험 보고에는 널리 쓰이는 지침이 있다(예: 시뮬레이션 실험의 최소 정보 기술, 계산 모델 신뢰성 평가 틀). 항목 이름과 요구는 제가 기억으로 단정하지 않고 원문을 확인해야 한다 | 조사 결과는 별도 보고서(출처 포함)로 남긴다. 조사는 정보 작성 모드의 수집 규칙(1 차 출처 확인)을 따라야 한다 | 확인 필요 |

### 8.4 영향 받는 앞의 판단

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| 계산 기록부 단계(§6) | 논문 활용이 목적이면 R1 과 함께 "보고서가 기록부 번호를 박는" 단계가 필요하다 | R1.5 (보고서 머리 연결)를 단계에 추가할 후보 | §6 |
| 엔진 정리의 우선순위 | 논문의 숫자는 재현돼야 한다 | 시계 결함(K1–K4)·벽시계 입력(K7)·시드 표류가 "논문 숫자가 바뀔 수 있는 원인"이라는 의미가 더해진다 | 1호·2호 |
| 가상 상수 문제 | 실측 상수 유입이 결론의 무게를 정한다 | 엔진·기록을 아무리 정교하게 해도 논문의 주장 수준은 실측에 매인다. 정보 작성 모드의 일이며 이 설계의 범위 밖이다 | 입문 보고서 §5 |

### 8.5 사용자에게 물을 것

| 4. 참고할 지침 조사 | 어떤 보고 지침을 따를지 | 원문 조사를 정보 작성 모드로 넘길지 | §8.3 |
