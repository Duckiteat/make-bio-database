# 승인 묶음 — 사람이 버튼 한 번으로 L6 변경을 승인하는 방식 (2026-11-02, 설계 초안)

> STG-12(자리별 담당과 권한 재검토)의 남은 일 — develop 손 쓰기를 L1·L2 로 좁히고 L6(문지기 · 설정 · 모드 표 · 자기 검사 시험)를 바꿀 때 사람 확인을 거는 방법. 사용자 결정 2026-11-02: "버튼 누르는 행위 자체를 사람 승인으로 본다 · 누를 때 숨기는 것 없이 무엇을 하는지 보여준다 · 위반되면 거부된다".
> 바탕: `docs/reports/2026-11-02-identity-keys.md`(열쇠 · 구역 · L5 두 열쇠) · RULE-0461(권한을 넓히는 길은 명시적 · 검증 가능 · 철회 가능) · RULE-0515(문지기).
> 칸: 범위 · 이유 · 영향 · 확인.

## 1. 왜 지금 방식으로는 안 되나 (2026-11-02 겪은 일)

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| 정책 파일을 바꾸면 바꾼 순간부터 새 정책이 적용된다 | 문지기는 `modes.json` 을 도구 호출마다 새로 읽고, 도구 뒤에 파일 앞뒤를 대조한다 | `except` 에 문지기 셋을 넣은 그 편집이 위반이 되어, 세션 안에서 L6 를 좁히는 변경을 끝낼 수 없었다 | `rebuild/gate.mjs` 24 · 191 · 215–232 행 |
| 문지기는 "누가 말했나"를 읽지 못한다 | 대화는 기계가 검증할 수 없고, 읽는 글에 섞인 "허락했다"는 말과 구별되지 않는다 | 사용자가 시켰어도 AI 세션이 바꾼 L6 는 위반 | RULE-0461 |
| 자동 모드에서는 ask 가 사람 클릭이 아닐 수 있다 | 자동 승인 분류기가 대신 처리할 수 있다 | "ask 를 통과했다 = 사람이 눌렀다" 는 이 환경에서 증거가 약하다 | 문지기 훅 입력 `permission_mode` (사용 가능 여부는 구현 때 확인) |

## 2. 승인 묶음 — 규약

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| **승인 단위 = 변경 묶음 하나** — 파일 목록 + 실제 바이트의 sha256 지문 | 수정마다 확인하면 승인이 잘게 쪼개져 뜻이 흐려지고, 영구 허용 규칙은 위험하다 | 승인은 그 묶음에만 닿고, 목록 밖 파일이나 다른 내용은 안 된다 | 지문이 다르면 거부 |
| **승인 화면은 도구가 만든다** — 바뀌는 파일 · 전체 diff · 파일마다 등급 · 구역 · 열쇠(저장 지도) · 건드리는 RULE · PERM · "넓힘 / 좁힘 / 느슨해짐" 판정 · 지문 | AI 가 쓴 요약은 빠뜨리거나 흐릴 수 있다 | 숨길 길이 없다. 사용자는 도구 출력만 본다 | 화면 첫 줄에 지문 — 버튼의 명령에도 같은 지문 |
| **적용은 승인한 그 바이트만** — 적용 순간에 지문을 다시 계산해 맞을 때만 쓴다 | 보여 준 것과 적용한 것이 다른 틈(보인 뒤 바꾸기)을 막는다 | 한 글자라도 다르면 쓰지 않고 거부 | 변이 시험 |
| **한 번 쓰면 끝** — 승인 기록(지문 · 시각 · 파일)을 영수증에 남기고 재사용 안 됨 | 영구 권한을 남기지 않는다 | 다음 L6 변경은 새 묶음 · 새 승인 | 영수증 사슬 |
| **버튼 = 사람의 행동** — 지문을 받는 명령에 ask 를 건다 | 모델이 만들 수 없는 행동이다 | 일반 모드에서는 이것으로 충분. 자동 모드는 4 의 서명 태그 | §4 |

## 3. 눌러도 거부되는 것

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| 권한을 **넓히는** 변경 — allow · 마스터 권한 추가, `except` · `protect` 제거, ask → allow | 넓히는 길은 설정에 적힌 standing 권한뿐(RULE-0461) | 승인 묶음에 넣을 수 없음. "거부됨 + 이유" 로 표시 | 시험 |
| **검토할 수 없는** 내용 — 바이너리 · 보이지 않는 제어 문자 · 너무 긴 한 줄 · 지나치게 큰 묶음 | 숨긴 내용이 클릭 한 번에 통과하는 것을 막는다 | 풀거나 쪼개서 다시 | 시험 |
| 자기 검사를 **느슨하게** 하는 변경 — FLOOR 내리기 · 변이 시험의 `find` 삭제 · 규칙 은퇴 · 시험 삭제 | 스스로를 통과시키는 길 | "느슨해짐" 으로 표시하고 별도 확인 없이는 거부 | 시험 |
| 승인 목록 **밖의** 파일이 같은 도구 호출에서 바뀜 | 묶음의 범위를 넘는다 | 위반(RULE-0515) 그대로 | 기존 도구 뒤 대조 |
| 보호 자리의 **셸 쓰기** (cp · sed 등) | 승인 명령을 거치지 않았다 | 위반 그대로 | 기존 도구 뒤 대조 |

## 4. 한계 — 숨기지 않는다

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| 하네스의 확인 창은 보통 명령 줄만 보여 주고 diff 는 보여 주지 않는다 | 승인 화면(diff)은 도구 출력에 있고 창에는 지문만 있다 | 사용자가 창의 지문과 도구 출력의 지문이 같은지 본다 — 화면 첫 줄이 안내 | 설계 한계로 명시 |
| 자동 모드(분류기가 승인)에서는 클릭이 사람의 행동이 아닐 수 있다 | 이 세션도 자동 모드로 보였다 | 그때는 사용자가 **서명한 git 태그**(키는 컨테이너에 없음)를 허용 서명자 목록과 대조하는 방식 | 구현 때 `permission_mode` 와 함께 확인 |
| 검증기 자체가 L6(문지기) 안에 있다 | 닭과 달걀 | 검증기와 "develop 손 쓰기 좁히기"를 **한 묶음**으로 만들어 처음 한 번만 사람이 적용(로컬 커밋 또는 서명 태그). 패치 초안: `workspace/STG-12-l6-patch.diff` | 묶음 하나 · 지문 하나 |

## 5. 만들 것 (순서)

| 범위 | 이유 | 영향 | 확인 |
|---|---|---|---|
| ① 승인 화면 생성기(`show`) — 순수 함수 | 보이는 것이 곧 적용되는 것 | 저장 지도 · 장부를 읽어 diff 와 판정을 만든다 | 합성 입력 시험 |
| ② 적용기(`apply-approved <지문>`) — 지문 대조 후에만 쓰기 | 승인한 바이트만 | 서기 쓰기 함수 호출 표(`authority.callers`)에 등록 | 변이 시험 |
| ③ 거부 규칙 §3 을 판정 함수로 | 클릭이 규칙을 대신하지 못한다 | RULE 번호 · 변이 시험 | `rules.mjs rule` |
| ④ develop 손 쓰기를 L1 · L2 로 · 자기 검사 시험은 승인 묶음으로만 | STG-12 의 끝나는 조건 | PERM-0017 의 ⚠ 가 줄어듦 | 권한 시험 |
| ⑤ 묶음 하나(①–④ + 시험 + 장부)를 지문과 함께 만들어 사람이 한 번 승인 | 처음 한 번은 사람의 적용 | 이후 L6 변경은 이 절차로 | 영수증 · 기록 |

## 6. 열린 질문

- 일반 모드와 자동 모드 중 어디서 승인할지 — 서명 태그를 처음부터 쓸지, 클릭으로 시작할지.
- `permission_mode` 가 훅 입력에 실제로 오는지(오면 자동 승인 모드에서는 클릭을 증거로 쓰지 않는다).
- 허용 서명자 목록을 어디에 둘지(저장 지도 · 권한 장부 · 새 장부).
